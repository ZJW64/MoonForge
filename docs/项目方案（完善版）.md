# MoonForge 项目方案（完善版）

> 本文件是对《MoonBit 元编程框架项目思路》（原稿）的**评审 + 修正 + 落地**版本。
> 修订日期：2026-09-22　｜　对标的赛事截止：2026-09-24（报名截止 + 项目验收，剩 **2 天**）
> 修订原则：**保留问题洞察，替换不可行的实现路径；把范围收敛到赛期内可交付、可验证的规模。**

---

## 0. 一句话结论

原稿的问题不是"想得不好"，而是**"想得太大、也太早"**——三层能力（派生规则注册 / AST 操作 API / 编译期执行引擎）全部建立在 MoonBit **目前并不存在**的编译器接口之上（用户自定义属性、AST 暴露、comptime 执行）。因此它今天既写不出可运行代码，也无法在赛期内验收。

修正方式是把同一个问题的解法**从"要求编译器开口子"换成"用户态工具链"**：

> **MoonForge = 一个用 MoonBit 编写的、源码到源码（source-to-source）的派生代码生成器。**
> 它读取 `.mbt` 中的类型定义与 `/// @derive(...)` 标记，按可插拔规则生成 MoonBit 源码，并在构建前生成 / 校验，让"为自定义类型批量生成样板代码"变成一条命令。

范围：**3 条内置规则 + 完整测试 + 可复现演示**。不依赖编译器内部 API，所以**今天就能跑起来、能被测试、能被评委复现**。

## 1. 原稿逐条评审

| # | 原稿要点 | 可行性核查 | 判定 | 修正动作 |
|---|---|---|---|---|
| 1 | `#meta.derive_rule(Trait)` 为自定义 trait 注册派生规则 | MoonBit **不支持用户自定义 attribute**；编译器只识别内置 derive 白名单，自定义 trait 派生直接报 **E4077**（官方文档明写："you cannot have MoonBit automatically derive a trait that you defined yourself"） | ❌ 不可行 | 改用 **doc comment 标记** `/// @derive(...)`：零语言改动、零编译器依赖、IDE 不报错、纯文本可解析 |

## 2. 事实依据（评委可自行核查）

1. **E4077 官方文档**（https://docs.moonbitlang.com/zh-cn/latest/language/error_codes/E4077.html）
   > "MoonBit 允许你为你的类型派生一些预定义特征的实现。这意味着**你无法让 MoonBit 自动派生你自定义的特征**。"
   示例 `struct A(Int) derive(T)`（T 为用户自定义 trait）直接编译失败。

2. **derive 的注册表在编译器内部**：`moonbitlang/moonbit-compiler` 的 `src/ast_derive.ml` 中，deriver 以 `Trait Type Path → Deriver Function` 的硬编码哈希表形式存在（`builtin:trait_eq` / `builtin:trait_show` / `moonbitlang/core/json:FromJson` …）。**没有对外的注册入口。**

3. **没有 proc-macro / comptime / 用户 attribute**：MoonBit 官方设计明确选择**编译期代码生成而非运行时反射**，但没有把代码生成能力开放给用户态。

**结论**：这不是语言缺陷，而是**工具链空位**。空位真实存在——但它位于"**用户态工具链**"这一层，而不是"编译器内部"这一层。原稿瞄准了后者，所以写不出代码；本方案改瞄前者，所以能交付。

## 3. 修正后的问题定义

**问题**：MoonBit 的 `derive(...)` 只覆盖编译器内置 trait 白名单（`Eq` / `Compare` / `Debug` / `Default` / `Show` / `Hash` / `ToJson` / `FromJson` / `Arbitrary`）。一旦需要"为自定义类型批量生成**语义化**代码"——数据校验、字段名枚举、结构化 diff、Builder、访问者——开发者只能：

- 逐类型手写样板代码 → **重复、易漏、随字段变更而漂移**；
- 或引入外部通用代码生成器 → **脱离包边界、无法访问私有字段、与 moon build 割裂**。

而编译器在可预见的版本内不会开放派生注册点。**所以在用户态补一个"派生代码生成器"，是这个生态当下唯一能落地、且立刻有用的解法。**

---

## 4. 定位与边界

**一句话定位**
> MoonForge 是一个用 MoonBit 编写的源码到源码派生代码生成器：读取 `.mbt` 中的类型定义与 `/// @derive(...)` 标记，按可插拔规则生成 MoonBit 源码，并在构建前自动生成 / 校验。

**明确不做的事（写进 README，主动接受检验）**
- ❌ 不是编译器插件，不修改 `moonc`，不依赖任何编译器内部 API；
- ❌ 不发明语言语法，不定义新的 attribute——只用**已经合法的 doc comment**；
- ❌ 不做运行时反射；
- ❌ 不生成"任意代码"——只生成规则定义的、可被测试覆盖的固定形状代码；
- ❌ 不声称扩展了 `derive()`——`derive()` 的行为完全不受影响。

## 5. 技术方案

### 5.1 流水线

```
 .mbt 源文件
     │  (1) 词法分析  lexer.mbt
     ▼
 Token 流
     │  (2) 语法分析（子集：只看类型定义，其余整体跳过）parser.mbt
     ▼
 类型模型 IR  type_model.mbt   { TypeDef, FieldDef, AttrMark }
     │  (3) 规则分派（@derive(...) → Rule）rule.mbt
     ▼
 每规则生成代码片段  rules/*.mbt
     │  (4) 组装 + 文件头 + 幂等约束  codegen.mbt
     ▼
 <源文件同目录>/<源文件主干名>_derive_gen.mbt
     │  (5) 与 moon build 并行编译（同包 → 可直接访问字段）
     ▼
 参与 moon check / moon test
```

### 5.2 关键设计决策（含取舍说明）

| 决策 | 选择 | 理由 / 取舍 |
|---|---|---|
| 生成文件落在哪 | **与源文件同目录** | MoonBit 的包边界是目录，私有字段仅同包可见。落在同目录才能直接访问字段，**无需把字段改成 `pub`**。代价：会往用户目录里写文件，用 `.gitignore` 约定 + 文件头 `DO NOT EDIT` 声明。 |
| 请求语法怎么表达 | **doc comment 标记** `/// @derive(...)` | 不改语言、不加依赖、IDE 与 `moon fmt` 都不会报错；代价是"标记"不会参与类型检查（写错规则名时靠 `moonforge check` 报出） |
| 解析范围 | **只解析类型定义**，函数体 / 表达式整体跳过 | 元编程只需要类型形状；跳过比解析代价低一个数量级，且对语言演进更鲁棒 |
| 生成时机 | **构建前独立阶段**（不是编译期） | 编译器没有钩子，只能外部驱动。诚实：这是"预生成"（pre-generation），不是 comptime |
| 幂等性 | 输出必须**字节稳定**：同一输入两次运行输出完全相同 | 让生成物可以进版本库、可以被 CI 校验漂移（drift check）——这是工程质量的核心可验证点 |
| 可扩展性 | 规则实现为**公开的 `Rule` 结构 + 注册表**，第三方可作为库依赖并注册自己的规则 | 不依赖编译器，所以"可扩展"是真的可扩展 |

### 5.3 请求语法（用户侧）

```moonbit
/// 用户信息
/// @derive(field_names, validate, diff)
pub struct User {
  /// 姓名
  /// @nonempty
  name : String

  /// 年龄
  /// @min(0) @max(150)
  age : Int

  email : String
}
```

- `@derive(a, b, c)` 写在**类型**的 doc comment 里；
- `@nonempty` / `@min(n)` / `@max(n)` / `@positive` 写在**字段**的 doc comment 里；
- 没有 `@derive` 的类型**不生成任何东西**（零侵入）。

### 5.4 生成结果示例（对应上面的 `User`）

```moonbit
// ------------------------------------------------------------------
// Generated by MoonForge v0.1.0 -- DO NOT EDIT.
// source : examples/models.mbt
// rules  : field_names, validate, diff
// regen  : moon run cmd/main -- gen examples
// ------------------------------------------------------------------

///|
pub fn User::field_names() -> Array[String] {
  ["name", "age", "email"]
}

///|
pub fn User::validate(self : User) -> Result[Unit, String] {
  if self.name == "" {
    return Err("User.name must not be empty")
  }
  if self.age < 0 || self.age > 150 {
    return Err("User.age must be in range [0, 150]")
  }
  Ok(())
}

///|
pub fn User::diff(self : User, other : User) -> Array[String] {
  let changed : Array[String] = []
  if self.name != other.name {
    changed.push("name")
  }
  if self.age != other.age {
    changed.push("age")
  }
  if self.email != other.email {
    changed.push("email")
  }
  changed
}
```

## 6. 本期交付范围

### 6.1 三条内置规则

| 规则 | 生成物 | 依赖条件 | 为什么选它 |
|---|---|---|---|
| `field_names` | `T::field_names() -> Array[String]` | 无 | 最简规则，用来暴露流水线全链路（解析 → IR → 生成） |
| `validate` | `T::validate(self) -> Result[Unit, String]` | 无 | 演示"**字段级标注驱动**"——同一条规则对不同类型生成不同代码，这是派生工具的价值核心 |
| `diff` | `T::diff(self, other) -> Array[String]` | 字段类型需实现 `Eq` | 演示"**逐字段展开**"，且直接对应原稿场景矩阵里的 Diffable |

> 原稿的「JSON / ORM / UI Props」等场景**不在本期范围**：它们需要引入序列化库或数据库依赖，会稀释测试投入。它们由 `Rule` 接口承接（见 6.2），作为 Roadmap。

### 6.2 扩展接口（"可扩展"的落点）

`Rule` 是公开类型，注册表是公开的 `Map[String, Rule]`：

```moonbit
pub struct Rule {
  name : String
  description : String
  gen : (TypeDef) -> String?   // None = 该类型不适用
}

pub fn default_registry() -> Map[String, Rule]
pub fn generate(source_name : String, src : String, rules : Array[String]) -> String
```

增加一条规则 = **新增一个文件 + 在注册表加一行**。第三方也可以把 MoonForge 作为库依赖，注入自己的规则集合。这是真实的可扩展性，而不是"预留了接口"的口号。

### 6.3 CLI

```
moonforge list-rules            # 列出所有已注册规则
moonforge explain <file.mbt>    # 打印解析出的类型模型与命中的标注（可解释性 / 调试）
moonforge gen   <dir|file>      # 生成 *_derive_gen.mbt
moonforge check <dir|file>      # 校验磁盘上的生成物是否与最新生成一致（CI 用，有漂移则非零退出）
```

## 10. 创新点（改为可验证的表述）

1. **在用户态补上了 MoonBit 缺失的派生注册点。** 依据 E4077，MoonBit 的 `derive()` 无法扩展；MoonForge 用合法语法（doc comment）而不是修改编译器，实现了"为自定义类型注册派生规则"的等价体验。**可验证**：`examples/` 里的 `User` 类型在没有任何手写实现的情况下获得了 `field_names` / `validate` / `diff` 三个方法。
2. **生成物可进版本库、可被 CI 校验漂移。** 输出字节稳定 + `moonforge check` 子命令，使"生成代码"从一次性脚本变成可持续维护的工程资产。**可验证**：`check` 在源文件被改动后返回非零退出码。
3. **生成的代码真的能过编译器。** 生成物随仓库提交，`moon check` 覆盖它——把工具的正确性交给编译器裁决。**可验证**：删掉生成文件则 `moon check` 失败。
4. **规则是一等公民而非插件配置。** `Rule` 是公开的 MoonBit 值，第三方可作为库依赖注入自己的规则；**可验证**：新增规则不需要改核心代码，只需在注册表加一行。
5. **"不做编译器插件"是一个经过论证的设计选择，而不是能力不足的遮羞布。** 第 2 节给出了编译器侧的事实依据，第 5.2 节给出了每个取舍的理由。
