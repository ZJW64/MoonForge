> 修订原则：**保留问题洞察，替换不可行的实现路径；把范围收敛到赛期内可交付、可验证的规模。**

## 0. 一句话结论

原稿的问题不是"想得不好"，而是**"想得太大、也太早"**——三层能力（派生规则注册 / AST 操作 API / 编译期执行引擎）全部建立在 MoonBit **目前并不存在**的编译器接口之上（用户自定义属性、AST 暴露、comptime 执行）。因此它今天既写不出可运行代码，也无法在赛期内验收。

修正方式是把同一个问题的解法**从"要求编译器开口子"换成"用户态工具链"**：

> **MoonForge = 一个用 MoonBit 编写的、源码到源码（source-to-source）的派生代码生成器。**
> 它读取 `.mbt` 中的类型定义与派生标记，按可插拔规则生成 MoonBit 源码，并在构建前生成 / 校验，让"为自定义类型批量生成样板代码"变成一条命令。

范围：**4 条内置规则 + 完整测试 + 可复现演示**。不依赖编译器内部 API，所以**今天就能跑起来、能被测试、能被评委复现**。

> v0.1/v0.2 的标记写成 doc comment（`/// @derive(...)`）；**v0.3.0 已改为语言级 trait impl**
> （`pub impl @derive.DeriveXxx for T with fn requested(_self) {}`），并把扩展点升级为
> `DeriveRule` SPI + 可替换的规则集。本文第 5～7 节保留当时的描述，**改动与理由见第 13 节**。

## 1. 原稿逐条评审

| # | 原稿要点 | 可行性核查 | 判定 | 修正动作 |
|---|---|---|---|---|
| 1 | `#meta.derive_rule(Trait)` 为自定义 trait 注册派生规则 | MoonBit **不支持用户自定义 attribute**；编译器只识别内置 derive 白名单，自定义 trait 派生直接报 **E4077**（官方文档明写："you cannot have MoonBit automatically derive a trait that you defined yourself"） | ❌ 不可行 | 改用**标记 trait + 普通 impl**（v0.3.0 起）：`pub impl @derive.DeriveValidate for T with fn requested(_self) {}`。同样是零语言改动、零编译器依赖，但**入口能被 `moon check` 真正编译**，拼错标记名在编译期就暴露 |
| 2 | `@meta.quote(...)` / `@meta.unquote(...)` 返回 AST 值 | 编译器**不暴露 AST**，MoonBit 也无 quote/unquote 机制；`@meta` 包不存在 | ❌ 不可行 | 改为**源码模板 + 占位符替换**（文本级 codegen）。文档中明确它**不是** AST 操作，不做概念挪用 |
| 3 | `#meta.comptime` 编译期执行引擎 | MoonBit 无 comptime，需要编译器支持 | ❌ 不可行 | 移除。等价能力用"**构建前运行生成器**"实现（外部阶段，而非编译期） |
| 4 | "与编译器团队协作，探索通过编译器插件 / `moon check --explain` 扩展点获得 AST 访问" | 跨组织协作，时间与结果都不由参赛者掌握 | ⏸ 冻结 | 移入 Roadmap，并**写清前置条件**（真正的阻塞点是什么） |
| 5 | `#meta.derive_rule(Serializable, target="wasm-gc")` 多后端感知 | `#cfg` 是编译器属性，框架无法插入；但"按后端选择不同规则变体"这一**效果**可以由 CLI 参数实现 | ⚠️ 部分可行 | 改为 CLI 参数 `--target wasm-gc|js|native` 选择规则变体，效果等价、实现真实 |
| 6 | 4 周里程碑（第 1~4 周） | 实际剩余 **2 天** | ❌ 不可行 | 重排为 2 天冲刺计划（见第 8 节） |
| 7 | 7 条场景矩阵（序列化 / ORM / UI Props …） | 是愿景清单，无一条可验收 | ⚠️ | 收敛为 **3 条已实现规则**（field_names / validate / diff）+ 一条公开的规则扩展接口 |
| 8 | "**首次**让 MoonBit 开发者能为自定义 trait 注册派生规则"、"**突破** derive 内置限制" | 无法证实，且实际并未突破语言边界——只是把上限从"编译器"挪到"用户态"；评委读代码就会发现没有 derive 扩展点 | ⚠️ 表述失真 | 改为可验证表述（见第 10 节） |
| 9 | 命名 MoonForge（月铸）"编译期铸造代码" | 名字本身没问题，但"框架"二字暗示编译器级依赖，与实际不符 | ⚠️ | **保留 MoonForge 名称**，定位描述改为"派生代码生成器 / 工具链"，避免夸大 |
| 10 | 与 `declare` 关键字协同（"后处理层"） | `declare` 是编译器关键字，框架无法挂载钩子；最多是文档级约定 | ⚠️ | 从"集成"降级为"可选的工程流程建议"，不作卖点 |

## 2. 事实依据（评委可自行核查）

1. **E4077 官方文档**（https://docs.moonbitlang.com/zh-cn/latest/language/error_codes/E4077.html）
   > "MoonBit 允许你为你的类型派生一些预定义特征的实现。这意味着**你无法让 MoonBit 自动派生你自定义的特征**。"
   示例 `struct A(Int) derive(T)`（T 为用户自定义 trait）直接编译失败。

2. **derive 的注册表在编译器内部**：`moonbitlang/moonbit-compiler` 的 `src/ast_derive.ml` 中，deriver 以 `Trait Type Path → Deriver Function` 的硬编码哈希表形式存在（`builtin:trait_eq` / `builtin:trait_show` / `moonbitlang/core/json:FromJson` …）。**没有对外的注册入口。**

3. **没有 proc-macro / comptime / 用户 attribute**：MoonBit 官方设计明确选择**编译期代码生成而非运行时反射**，但没有把代码生成能力开放给用户态。

**结论**：这不是语言缺陷，而是**工具链空位**。空位真实存在——但它位于"**用户态工具链**"这一层，而不是"编译器内部"这一层。原稿瞄准了后者，所以写不出代码；本方案改瞄前者，所以能交付。

## 3. 修正后的问题定义

**问题**：MoonBit 的 `derive(...)` 只覆盖编译器内置 trait 白名单（`Eq` / `Compare` / `Debug` / `Default` / `Show` / `Hash` / `ToJson` / `FromJson` / `Arbitrary`）。一旦需要"为自定义类型批量生成**语义化**代码"——数据校验、字段名枚举、结构化 diff、Builder、访问者——开发者只能：

- 逐类型手写样板代码 → **重复、易漏、随字段变更而漂移**；
- 或引入外部通用代码生成器 → **脱离包边界、无法访问私有字段、与 moon build 割裂**。

而编译器在可预见的版本内不会开放派生注册点。**所以在用户态补一个"派生代码生成器"，是这个生态当下唯一能落地、且立刻有用的解法。**

## 4. 定位与边界

**一句话定位**
> MoonForge 是一个用 MoonBit 编写的源码到源码派生代码生成器：读取 `.mbt` 中的类型定义与 `impl @derive.DeriveXxx for T` 标记，按可插拔规则生成 MoonBit 源码，并在构建前自动生成 / 校验。（v0.1/v0.2 的入口是 `/// @derive(...)`，v0.3.0 已改。）

**明确不做的事（写进 README，主动接受检验）**
- ❌ 不是编译器插件，不修改 `moonc`，不依赖任何编译器内部 API；
- ❌ 不发明语言语法，不定义新的 attribute——入口是**本来就合法的 trait impl**（v0.1/v0.2 用的是 doc comment，v0.3.0 已改）；
- ❌ 不做运行时反射；
- ❌ 不生成"任意代码"——只生成规则定义的、可被测试覆盖的固定形状代码；
- ❌ 不声称扩展了 `derive()`——`derive()` 的行为完全不受影响。

## 5. 技术方案

### 5.1 流水线

```
 .mbt 源文件
     │  (1) 词法分析  lexer.mbt
     ▼
 Token 流
     │  (2) 语法分析（子集：只看类型定义，其余整体跳过）parser.mbt
     ▼
 类型模型 IR  type_model.mbt   { TypeDef, FieldDef, AttrMark }
     │  (3) 规则分派（标记 impl → &DeriveRule，trait 对象）rule.mbt
     ▼
 每规则生成代码片段  rules/*.mbt
     │  (4) 组装 + 文件头 + 幂等约束  codegen.mbt
     ▼
 <源文件同目录>/<源文件主干名>_derive_gen.mbt
     │  (5) 与 moon build 并行编译（同包 → 可直接访问字段）
     ▼
 参与 moon check / moon test
```

### 5.2 关键设计决策（含取舍说明）

| 决策 | 选择 | 理由 / 取舍 |
|---|---|---|
| 生成文件落在哪 | **与源文件同目录** | MoonBit 的包边界是目录，私有字段仅同包可见。落在同目录才能直接访问字段，**无需把字段改成 `pub`**。代价：会往用户目录里写文件，用 `.gitignore` 约定 + 文件头 `DO NOT EDIT` 声明。 |
| 请求语法怎么表达 | **标记 trait 的真实 impl**（v0.3.0） | 不放宽任何语法、不加任何依赖；且因为是真 `impl`，**标记会参与类型检查**（拼错标记名在 `moon check` 阶段就报 unknown trait）。<br>v0.1/v0.2 曾用 doc comment `/// @derive(...)`：同样不改语言，但标记不参与类型检查、且是"只有本工具认识"的私有约定，v0.3.0 已废弃 |
| 解析范围 | **只解析类型定义**，函数体 / 表达式整体跳过 | 元编程只需要类型形状；跳过比解析代价低一个数量级，且对语言演进更鲁棒 |
| 生成时机 | **构建前独立阶段**（不是编译期） | 编译器没有钩子，只能外部驱动。诚实：这是"预生成"（pre-generation），不是 comptime |
| 幂等性 | 输出必须**字节稳定**：同一输入两次运行输出完全相同 | 让生成物可以进版本库、可以被 CI 校验漂移（drift check）——这是工程质量的核心可验证点 |
| 可扩展性 | 规则实现为 **`pub(open) trait DeriveRule`**（SPI），规则集是 `Array[&DeriveRule]` 的**异构 trait 对象数组**，由调用方显式传入 | 不依赖编译器，所以"可扩展"是真的可扩展：第三方只需实现一个 trait 并把对象放进集合，**不必成为工具的一部分**（v0.1/v0.2 的"注册表加一行"要求改本仓库，v0.3.0 已升级） |

### 5.3 请求语法（用户侧，v0.3.0）

```moonbit
/// 用户信息
pub struct User {
  /// 姓名
  /// @nonempty
  name : String

  /// 年龄
  /// @min(0) @max(150)
  age : Int

  email : String
}

///|
pub impl @derive.DeriveFieldNames for User with fn requested(_self) {}

///|
pub impl @derive.DeriveValidate for User with fn requested(_self) {}

///|
pub impl @derive.DeriveDiff for User with fn requested(_self) {}
```

- 派生请求写成**标记 trait 的真实 impl**（`@derive.DeriveXxx`），放在类型所在文件；
- `@nonempty` / `@min(n)` / `@max(n)` / `@positive` 仍写在**字段**的 doc comment 里
  —— 它们是规则私有的输入，由具体规则解释；
- 没有标记的类型**不生成任何东西**（零侵入）；
- impl 的书写顺序 = 生成物中 impl 的顺序。

### 5.4 生成结果示例（对应上面的 `User`）

```moonbit
// ------------------------------------------------------------------
// Generated by MoonForge v0.1.0 -- DO NOT EDIT.
// source : examples/models.mbt
// rules  : field_names, validate, diff
// regen  : moon run cmd/main -- gen examples
// ------------------------------------------------------------------

///|
pub fn User::field_names() -> Array[String] {
  ["name", "age", "email"]
}

///|
pub fn User::validate(self : User) -> Result[Unit, String] {
  if self.name == "" {
    return Err("User.name must not be empty")
  }
  if self.age < 0 || self.age > 150 {
    return Err("User.age must be in range [0, 150]")
  }
  Ok(())
}

///|
pub fn User::diff(self : User, other : User) -> Array[String] {
  let changed : Array[String] = []
  if self.name != other.name {
    changed.push("name")
  }
  if self.age != other.age {
    changed.push("age")
  }
  if self.email != other.email {
    changed.push("email")
  }
  changed
}
```

## 6. 本期交付范围

### 6.1 三条内置规则（v0.1/v0.2 时期；v0.3.0 起为 4 条，新增 `to_pairs`）

| 规则 | 生成物 | 依赖条件 | 为什么选它 |
|---|---|---|---|
| `field_names` | `T::field_names() -> Array[String]` | 无 | 最简规则，用来暴露流水线全链路（解析 → IR → 生成） |
| `validate` | `T::validate(self) -> Result[Unit, String]` | 无 | 演示"**字段级标注驱动**"——同一条规则对不同类型生成不同代码，这是派生工具的价值核心 |
| `diff` | `T::diff(self, other) -> Array[String]` | 字段类型需实现 `Eq` | 演示"**逐字段展开**"，且直接对应原稿场景矩阵里的 Diffable |

> 原稿的「JSON / ORM / UI Props」等场景**不在本期范围**：它们需要引入序列化库或数据库依赖，会稀释测试投入。它们由 `Rule` 接口承接（见 6.2），作为 Roadmap。

### 6.2 扩展接口（"可扩展"的落点）

**v0.4.0**：规则是一个公开的 SPI trait，规则集是公开的**异构 trait 对象数组**，
输入是**统一契约** `DeriveInput`（规则看不到解析器的 IR）：

```moonbit
pub(open) trait DeriveRule {
  fn head(Self) -> RuleHead                      // 契约一：身份
  fn generate(Self, DeriveInput) -> Fragment?    // 契约二（输入）+ 契约三（输出）
}

pub fn all() -> Array[&@forge.DeriveRule]      // 内置规则集
pub fn generate(source_name : String, src : String,
                rules : Array[&DeriveRule], version : String) -> GenOutcome
```

增加一条规则 = **实现一个 trait + 把对象放进集合**。
第三方可以只依赖本包、把自己的规则与内置规则**合成新集合**再调用 `generate`，
**不需要修改本仓库的任何源码** —— `examples/extension/` 是一个可运行的完整样例
（自带目标 trait `ToCsv`、标记 trait `DeriveToCsv`、规则 `ToCsvRule`），
`tocsv_wbtest.mbt` 用 5 条测试把它钉住。

> v0.1/v0.2 用的是 `Rule` 结构体 + 注册表数组，扩展需要改本仓库；
> v0.3.0 把它升级为 SPI trait + 可替换集合：**扩展不再要求你成为工具的一部分。**

### 6.3 CLI

```
moonforge list-rules            # 列出所有已注册规则
moonforge explain <file.mbt>    # 打印解析出的类型模型与命中的标注（可解释性 / 调试）
moonforge gen   <dir|file>      # 生成 *_derive_gen.mbt
moonforge check <dir|file>      # 校验磁盘上的生成物是否与最新生成一致（CI 用，有漂移则非零退出）
```

## 7. 测试策略与验收映射

### 7.1 测试分层

| 层 | 覆盖对象 | 形式 | 数量级 |
|---|---|---|---|
| L1 单元 | 词法分析：ASCII 标识符、中文标识符、`///|` 块分隔、注释、字符串字面量跳过 | `*_test.mbt`，`inspect()` 断言 | ~10 |
| L2 单元 | 语法分析：`struct` / `pub struct` / 多行字段 / 泛型字段类型 / 枚举 / 函数体跳过 / 非法输入不 panic | `inspect()` | ~12 |
| L3 规则 | 每条规则至少 3 个用例：正常、边界（无字段 / 标注不适用）、含中文与泛型 | `inspect()` | ~10 |
| L4 金样 | 端到端：固定输入 `.mbt` → 断言输出**逐字节**等于预期文本（内嵌字符串，不依赖文件 IO，测试可离线跑） | `inspect()` | 3 |
| L5 幂等 | 同一输入连续生成两次，输出必须完全相同（`generate(generate)` 不漂移） | `inspect()` | 2 |
| L6 集成（真编译） | `examples/models_derive_gen.mbt` 提交进仓库，`moon check` 保证**生成的代码真的能通过 MoonBit 编译器** | 构建命令 + CI | 1 |
| L7 端到端 CLI | `moonforge gen` 后 `moonforge check` 退出码为 0；改动源文件后 `check` 退出码非 0 | 脚本 + CI | 2 |
| L8 单元 | CLI 地基：宿主 argv 前缀归一化、`is_command` 白名单、路径拆分与拼接（正 / 反斜杠） | `cmd/main/main_wbtest.mbt`，`inspect()` 断言 | ~7 |

> **L6 是这套方案最关键的一条**：它把"工具输出的代码是正确的"从"我说它对"变成"编译器说它对"。

## 10. 创新点（改为可验证的表述）

1. **在用户态补上了 MoonBit 缺失的派生注册点。** 依据 E4077，MoonBit 的 `derive()` 无法扩展；MoonForge 用**合法语法（真实 trait impl）**而不是修改编译器，实现了"为自定义类型注册派生规则"的等价体验。**可验证**：`examples/` 里的 `User` 类型在没有任何手写实现的情况下获得了 `FieldNames` / `Validate` / `Diff` / `ToPairs` 四个 trait 的实现；且标记 impl 本身能被 `moon check` 编译。
2. **生成物可进版本库、可被 CI 校验漂移。** 输出字节稳定 + `moonforge check` 子命令，使"生成代码"从一次性脚本变成可持续维护的工程资产。**可验证**：`check` 在源文件被改动后返回非零退出码。
3. **生成的代码真的能过编译器。** 生成物随仓库提交，`moon check` 覆盖它——把工具的正确性交给编译器裁决。**可验证**：删掉生成文件则 `moon check` 失败。
4. **规则是一等公民而非插件配置。** 规则是一个公开的 SPI trait，规则集是 `Array[&DeriveRule]`；第三方可作为库依赖注入自己的规则；**可验证**：`examples/extension/` 在**未修改本仓库任何源码**的前提下新增了一条可用规则，并有 5 条测试作证。
5. **"不做编译器插件"是一个经过论证的设计选择，而不是能力不足的遮羞布。** 第 2 节给出了编译器侧的事实依据，第 5.2 节给出了每个取舍的理由。

## 13. 修订记录：v0.3.0（2026-09-23）

### 13.1 为什么要改

v0.1/v0.2 的入口是 doc comment 里的 `/// @derive(validate, diff)`。它在当时的取舍下是合理的
（零语言改动、IDE 不报错），但有三处硬伤：

| 硬伤 | 后果 |
|---|---|
| **入口不参与类型检查** | 标记名拼错不会有任何提示，只能等 `moonforge check` 来猜 |
| **入口是"只有本工具认识"的私有约定** | 换个工具、换个人接手就失效；它不是语言事实，只是一段注释 |
| **扩展点是"改本仓库的注册表数组"** | 想加规则就必须成为工具的一部分，生态价值弱 |

评审意见指出的正是这三点：能力受限、可复用性弱、扩展机制不是语言级的。

### 13.2 改成了什么

**三段式，每段都是语言里真实存在的东西：**

| 段 | 载体 | 说明 |
|---|---|---|
| 目标 trait | `FieldNames` / `Validate` / `Diff` / `ToPairs`（`moonforge/derive`） | 普通 MoonBit trait，用户可实现、也可自定义同类 |
| 标记 trait | `DeriveFieldNames` / … | 用户写一行 `pub impl @derive.DeriveXxx for T with fn requested(_self) {}` 即提交一次请求 |
| 规则 | `pub(open) trait DeriveRule` | `head()` 给身份，`generate()` 给代码；规则集是 `Array[&DeriveRule]` |

**为什么入口不能用 `derive(...)`**：编译器的 `derive(...)` **只认内置 trait 白名单**，
对自定义 trait 直接报 `Don't know how to derive trait X`（E4077）—— 它恰恰是这套工具要绕开的限制，
不能反过来当扩展入口。普通 `impl` 没有这个限制。

**为什么标记 trait 必须带一个方法**：MoonBit 语法不允许 `impl T for X {}` 空块
（`Invalid grouped impl declarations`），所以标记 trait 带 `fn requested(Self) -> Unit`，
由请求方写空方法体。这个空方法不是装饰，是语法的硬要求。

### 13.3 顺带修掉的一个真实缺陷（列宽预算）

改动过程中发现：生成物是提交进仓库的，用户迟早会跑 `moon fmt`；
而新的 impl 头（`pub impl @derive.Validate for User with fn validate(self) -> Result[Unit, String] {`）
长达 83～85 列，**`moonfmt` 会把 83 列起的行折开**（82 列及以下保持原样，实测）。

结果：格式化一次 → 生成物字节与格式化结果不一致 → `check` 永久报漂移，
而且 `gen` 也治不好（它照旧写单行版）。

修法两条：

1. 生成的 impl 头**不写返回类型**（返回类型由目标 trait 声明唯一决定），
   impl 头从 83～85 列降到 58～61 列，留出约 20 列余量；
2. 新增列宽守卫：真的超预算时在生成阶段给出可操作的诊断（缩短类型名 / 用更短的包别名 / 缩短签名），
   而不是让用户在 `moon fmt` 与 `check` 之间反复横跳。

边界值不靠估计：`scripts/fmt_budget_probe.sh` 用**真实 `moonfmt`** 现场构造预算两侧的 impl 头，
断言"预算内保持、超预算折开"，并已接进 `scripts/e2e.sh` 第 4 阶段；
量不到预期就非零退出，换工具链时不会悄悄失效。

### 13.4 可验证的落点

| 主张 | 复现命令 | 期望 |
|---|---|---|
| 入口是语言级事实 | `moon check` | 通过；把 `DeriveValidate` 拼错则报 unknown trait |
| 标记 impl 能被编译器编译 | `moon check` | 通过（标记是普通 `impl`，不是注释） |
| 规则集可替换、可组合 | `moon test --target js` | `examples/extension/tocsv_wbtest.mbt` 5 条用例通过 |
| 生成物与格式化器逐字节一致 | `bash scripts/e2e.sh` | 第 4 阶段全过 |
| 列宽边界是实测的 | `bash scripts/fmt_budget_probe.sh` | `OK: 列宽预算 82 实测成立（4 条里 4 条折开）` |

### 13.5 被放弃的方案（记录一下，免得后人重走）

| 方案 | 为什么放弃 |
|---|---|
| 继续用 `derive(CustomTrait)` 当入口 | 编译器直接拒绝（E4077），无法绕过 |
| 用空 impl 当标记：`impl DeriveX for T {}` | MoonBit 语法错误（`Invalid grouped impl declarations`） |
| 一条 `impl ... with` 块里写多个方法 | 编译失败；一个块只能一个方法，所以 SPI 收敛为两个方法 |
| 让规则自己拼出完整的 `pub impl ... {` 头 | 规则会各自与"列宽预算 / `///|` 位置 / 前缀复用"这些全局约定耦合，一处改动要改所有规则；改为由生成器统一拼头、规则只提供成员体 |
| 给 `impl` 头写返回类型，靠"手动折行"对齐 `moonfmt` | 要复刻格式化器的折行算法，等于把工具链实现细节焊进本项目；改用"不写返回类型"从根上避开 |

### 14.3 输入契约的抽出

- 新增 `derive_input.mbt`：`DeriveInput { type_name, body, fields, request }` 与
  `DeriveRequest { prefix, marker, line }`。规则签名从 `generate(Self, TypeDef)`
  改为 `generate(Self, DeriveInput)`。
- 契约的保证写在同一处：`type_name` 不含包前缀；`fields` 当且仅当有具名字段时非空；
  `f.ty` 已 trim / 无尾随逗号 / 无换行 / 空白折叠；字段顺序 = 声明顺序；
  `request.marker` 不含包前缀、`line` 从 1 起。
- 6 条契约测试（`derive_input_wbtest.mbt`）+ 1 条**前端无关性**测试
  （不经 parser 手工构造 `DeriveInput` 直接生成）。**契约必须被测试钉住**，
