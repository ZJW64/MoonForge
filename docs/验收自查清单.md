## 3. `scripts/e2e.sh` 的 6 个阶段分别证明了什么

| 阶段 | 证明的主张 | 失败会意味着什么 |
|---|---|---|
| 1 漂移检查 | 仓库里已提交的生成物与当前源文件**一致**；位置参数结构体没有产出任何方法 | 生成物过时，或位置参数结构体又"借用"了下一个声明的字段体 |
| 2 测试 | 126 个用例全过 | 词法 / 语法 / 规则 / 幂等 / 集成某一层退化 |
| 3 真编译 | 生成出来的代码**能被编译器接受** | 生成器输出了非法 MoonBit —— 最严重的一类缺陷 |
| 4 格式化稳定性 | 仓库已格式化；列宽预算用真实 `moonfmt` 现场实测；且生成物与 `moon fmt` 的字节**逐字节一致** | 用户跑一次 `moon fmt` 就会让 `check` 永久报漂移，而 `gen` 修不好 |
| 5 CRLF 容忍 | 生成物被换成 CRLF 后 `check` 仍通过 | Windows 上（`core.autocrlf=true`）会误报漂移 |
| 6 闭环与退出码契约 | 漂移 → `1`；`gen` 后 → `0`；路径错 / 非 `.mbt` / 传目录 → `2`；去掉派生标记后 `gen` 清理残留生成物 | CI 会"假绿"，或用户陷入"照提示跑 `gen` 也修不好"的死循环 |

## 4. "工作有效"这件事怎么证明

不是靠自我声明，而是三条可执行的证据链：

| 主张 | 怎么验（命令） | 为什么这是证据 |
|---|---|---|
| 生成代码真的能用 | `moon test --target js`，其中 `examples/models_wbtest.mbt` 直接调用 `User::validate` / `User::diff` / `User::field_names` / `User::to_pairs` | 这些方法在仓库里**没有任何手写实现**——唯一来源是生成器 |
| 生成代码真的合法 | `rm examples/models_derive_gen.mbt && moon check` → 失败；`moon run cmd/main -- gen examples && moon check` → 恢复 | 正确性由**编译器**裁决，不由工具的自我声明裁决 |
| 漂移真的能被拦住 | `moon run cmd/main -- check <改了源码的副本>` → 退出码 `1` | CI 的核心价值；这条负例在 e2e 第 6 阶段被固化 |

## 5. "可扩展"这件事怎么证明

这一轮把"可扩展"从**口号**变成了**可运行的事实**，证据链有四条：

| 主张 | 怎么验（命令） | 为什么这是证据 |
|---|---|---|
| 派生目标是**普通 trait**，不是工具内部的名字 | 读 [`derive/derive.mbt`](../derive/derive.mbt) | 目标是 `FieldNames` / `Validate` / `Diff` / `ToPairs` —— 用户可以自己实现，也可以自己定义同类 trait；标记是 `DeriveFieldNames` 等，形状与第三方样例里的 `DeriveToCsv` 完全一致 |
| 规则是 **SPI trait**，规则集是**异构对象数组** | 读 [`rule.mbt`](../rule.mbt) 的 `pub(open) trait DeriveRule` 与 [`rules/registry.mbt`](../rules/registry.mbt) 的 `Array[&@forge.DeriveRule]` | 遍历时只调 trait 方法，不关心背后是什么具体类型 —— 这正是"规则数量可以增长"的技术前提 |
| **第三方不改内核就能加规则** | `moon test --target js`，其中 [`examples/extension/tocsv_wbtest.mbt`](../examples/extension/tocsv_wbtest.mbt) 5 条用例 | 该样例自带 `ToCsv` / `DeriveToCsv` / `ToCsvRule`，把内置规则与自己的规则合成新集合后直接生成，**未修改 moonforge 任何一行源码**；并覆盖"前缀被复用"、"只用自己的规则集时内置规则完全不出场"、"未注册标记被明确报出" |
| 有可照抄的完整流程 | 读 [`docs/扩展规则指南.md`](扩展规则指南.md) | 含三段式契约、SPI 两个方法的由来、白名单纪律、反面例子、**成员体不写返回类型的硬约束**、收尾自查清单 |

一句话总结这一轮的变化：**上一版的扩展点是"改一个数组"，这一版的扩展点是"实现一个 trait 并把对象放进集合"。** 前者要求你成为工具的一部分，后者不要求。

## 6. "独立核心贡献"这件事怎么证明

评审意见是"已有 parser、MoonMacro、codegen 可复用，申报剩余主要为少量模板与生成物管理"。
本项目的回答不是形容词，而是**先把不该算贡献的部分摘出去，再用测试证明剩下那层是真的**：

| 主张 | 怎么验 | 证据 |
|---|---|---|
| 解析 / 宏 / 生成代码**不算**本项目的贡献 | —— | 已有 `moonc`、[tree-sitter-moonbit](https://github.com/moonbitlang/tree-sitter-moonbit)、[MoonMacro](https://mooncakes.io/docs/faaaaa3/moonmacro)；本仓库 `lexer.mbt` / `parser.mbt` 只是**前端适配层**，见 [`核心贡献边界.md`](核心贡献边界.md) 第 1 节 |
| **前端可替换** | `moon test --target js` | `rules/rules_wbtest.mbt` 的"前端无关"用例：**完全不经过 parser**，手工构造 `DeriveInput` 字面量直接调用规则并断言生成结果 |
| **输入契约成立** | `moon test --target js` | `derive_input_wbtest.mbt` 6 条：归一化（无尾随逗号 / 无换行 / 空白折叠）、请求三字段传递、只有具名字段才非空、顺序、注解原样保留 |
| **规则可替换（不改内核）** | `moon test --target js` | `examples/extension/tocsv_wbtest.mbt` 5 条 |
| **输出是 fmt 的固定点** | `bash scripts/fmt_budget_probe.sh`；`bash scripts/e2e.sh` 第 4 阶段 | 82 列边界实测成立；生成物与 `moonfmt` 输出逐字节相同 |
| **消融：删掉前端项目还在** | 上述测试即可 | 契约层与规则不 import parser 的输出类型（规则签名是 `generate(Self, DeriveInput)`） |

一句话：**解析器是别人的，生成代码谁都会；本项目的独立贡献是把"派生"定义成三份契约，
并证明这三份契约能被编译器、格式化器、CI 同时复核。**

## 9. 复现步骤（给评委的最短路径）

```bash
git clone https://github.com/ZJW64/MoonForge && cd MoonForge
moon check                                # 1. 含生成代码一起编译
moon run cmd/main -- explain examples/models.mbt   # 2. 看工具如何解释自己
moon test --target js                     # 3. 126 个用例
bash scripts/e2e.sh                       # 4. 6 个阶段端到端
```

第 2 步的输出值得一看：它会把 `Point` 显示为 `struct(位置参数)`，并对三条规则各给一句
`[--] ... 不适用：Point 是位置参数（元组）结构体，没有具名字段`。
**"不生成"和"生成"一样要被解释**——这是本项目对"可解释"的具体理解。

## 10. 已知的、非缺陷的环境限制

| 现象 | 说明 |
|---|---|
| `moon test --target native` 报 `no system C compiler found` | 本机没有 C 编译器。`js` 与 `wasm-gc` 两个后端均 126/126 通过；`native` 后端不是本项目的验收口径 |
| `moon fmt --check` 在"有差异"时退出码为 `127`（不是 `1`） | MoonBit 工具链的实际行为，CI 只判定非零。已在 `.github/workflows/ci.yml` 注释中写明，避免后来人误判为脚本 bug |
| `wasm-gc` 后端的出错路径会附带 `RuntimeError: unreachable` 回溯 | `wasm-gc` 没有标准退出原语。因此 CI 的漂移检查固定用默认的 `js` 后端 |
