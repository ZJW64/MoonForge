## 2. 分步演示（讲清楚每一环在做什么）

### 2.1 看工具认识哪些规则

```bash
$ moon run cmd/main -- list-rules
已注册的派生规则。派生入口是在类型所在文件里写一行真实 trait impl：

    pub impl @derive.DeriveXxx for <类型> with fn requested(_self) {}

  field_names
      标记 DeriveFieldNames  →  生成 impl FieldNames
      为 struct 实现 FieldNames::field_names，顺序与字段声明一致
  validate
      标记 DeriveValidate  →  生成 impl Validate
      为 struct 实现 Validate::validate，由字段注解 @nonempty/@min/@max/@positive 驱动
  diff
      标记 DeriveDiff  →  生成 impl Diff
      为 struct 实现 Diff::diff，返回发生变化的字段名（字段类型需实现 Eq）
  to_pairs
      标记 DeriveToPairs  →  生成 impl ToPairs
      为 struct 实现 ToPairs::to_pairs，只包含 String 字段（其余字段跳过并留说明行）
```

注意 `list-rules` 的第一行：它**同时给出了入口写法**。规则的四个身份字段
（规则键 / 标记 trait / 目标 trait / 描述）逐条列出来，是因为用户真正要写的是
**标记 trait 名**（`DeriveFieldNames`），而不是规则键（`field_names`）——
这对新手是最容易搞混的一处，所以工具把它摆在明面上。

### 2.2 看一份真实的输入

打开 `examples/models.mbt`。它就是**普通 MoonBit 代码**，没有任何新语法：

```moonbit
///|
/// 用户信息。
///
/// `to_pairs` 只收 `String` 字段：`age` 是 Int，工具不会替用户决定
/// "Int 该怎么变成字符串"，因此跳过并在生成文件里留下说明行。
pub(all) struct User {
  /// 姓名
  /// @nonempty
  name : String
  /// 年龄
  /// @min(0) @max(150)
  age : Int
  /// 电子邮箱 —— 没有校验注解，因此不会产生任何检查代码
  email : String
} derive(Eq, Debug)

///|
/// 为 User 请求四项派生。四行 impl 的书写顺序就是生成物中四段 impl 的顺序。
pub impl @derive.DeriveValidate for User with fn requested(_self) {}

///|
pub impl @derive.DeriveDiff for User with fn requested(_self) {}

///|
pub impl @derive.DeriveFieldNames for User with fn requested(_self) {}

///|
pub impl @derive.DeriveToPairs for User with fn requested(_self) {}
```

（`moon fmt` 会把空的 `{}` 方法体展开成两行 —— 它仍是空体，语义不变。上面为了排版紧凑保留了一行写法。）

标记是**真实的 `impl`**，所以它会被 `moon check` 真正编译：把 `DeriveValidate`
拼成 `DeriveValidat`，编译期就会报"unknown trait"，不必等工具来猜。

同一个文件里还有另外三个"反面样本"，它们是演示的重点：

| 声明 | 演示什么 |
|---|---|
| `Order` | `quantity` 是 `Int` 却写了 `@nonempty` → **跳过并留说明行**，不生成语义可疑的代码 |
| `enum Status` | 没有任何派生标记 → 工具**完全不碰**（零侵入） |
| `struct Point(Int, Int)` | 有标记但**没有具名字段** → **拒绝生成并说清原因**，而不是生成一个返回空数组的 `field_names` |

### 2.4 生成

```bash
$ moon run cmd/main -- gen examples
  [warn] models.mbt: 规则 `field_names` 不适用于 Point（第 113 行）：Point 是位置参数（元组）结构体，没有具名字段
  [warn] models.mbt: 规则 `validate` 不适用于 Point（第 118 行）：Point 是位置参数（元组）结构体，没有具名字段
  [warn] models.mbt: 规则 `diff` 不适用于 Point（第 123 行）：Point 是位置参数（元组）结构体，没有具名字段
  generated examples/models_derive_gen.mbt  [User.validate, User.diff, User.field_names, User.to_pairs, Order.field_names, Order.validate, Order.diff]

moonforge: 扫描 2 个源文件，生成 1 个，清理 0 个，警告 3 条
```

打开 `examples/models_derive_gen.mbt` 查看生成结果，注意：

- 文件头写明版本、来源、**当前入口写法**与重现命令；
- 生成的 impl 头是 `pub impl @derive.Validate for User with fn validate(self) {`
  —— 路径前缀**复用你在源文件里用的别名**（这里写成 `@d` 就会生成 `@d`），
  且**不写返回类型**（返回类型由 trait 声明决定；写上去会把这行撑到 83 列以上，
  被 `moon fmt` 折开，见第 4 节）；
- 说明行 `// moonforge: 跳过 Order.quantity 的校验注解（类型 Int 不在 ... 白名单内）` 解释了"为什么不生成"；
- **生成方法在仓库里没有任何手写实现**。

> `gen` 是**幂等**的：连跑两次，输出**逐字节相同**（`codegen_wbtest.mbt` 里有断言）。
> 它还会**清理残留生成物**：源文件里已经没有派生标记时，同名的 `*_derive_gen.mbt` 会被删除，
> 避免 `check` 一直报"多余的生成文件"而 `gen` 又修不好的死循环。

生成物是**提交进仓库**的，所以它一直在参与编译：

```bash

```


### 2.7 演示漂移检查（CI 的核心价值）

> 下面在 `_build/` 的副本里做，**不动仓库**；`scripts/e2e.sh` 第 6 阶段就是同一套动作。

```bash
$ mkdir -p _build/demo && cp examples/models.mbt _build/demo/

# 改动源文件但故意不重新生成
$ printf '\n///|\npub struct DriftProbe {\n  k : String\n}\n\n///|\npub impl @derive.DeriveFieldNames for DriftProbe with fn requested(_self) {}\n' >> _build/demo/models.mbt

$ moon run cmd/main -- check _build/demo
  [drift] 内容过期：_build/demo/models_derive_gen.mbt

moonforge: 检测到 1 处生成物漂移（已扫描 1 个文件）。
请运行 `moon run cmd/main -- gen <dir>` 重新生成并提交。
$ echo $?
1

# 重新生成后恢复
$ moon run cmd/main -- gen _build/demo
$ moon run cmd/main -- check _build/demo
moonforge: 已扫描 1 个源文件，生成物与源文件一致，无漂移
```

**这里有一个值得讲的细节**：`check` 的"未过期"判定是基于**源文件重新生成一遍、再和磁盘上的字节对比**，而不是比对时间戳。所以它不依赖文件系统时间精度，跨机器、跨时区、`git clone` 之后（源码与生成物的 mtime 顺序不可控）结果都一样。

退出码约定：`0` 成功；`1` 检出漂移；`2` 参数或路径有误。任何错误都会落成**一行** `moonforge: ...` 提示，不会把运行期堆栈喷进 CI 日志。

| 命令 | 触发场景 | 退出码 |
|---|---|---|
| `moonforge check <dir>` | 源文件与生成物一致 | `0` |
| `moonforge check <dir>` | 源文件改过、生成物未更新 | `1` |
| `moonforge check <path>` | `path` 不存在 / 不是 `.mbt` / 目录里没有 `.mbt` | `2` |

最后一行是刻意加的防"假绿"：以前路径写错会静默返回 0，CI 显示绿色但一个文件都没检查。

把 `check` 接进 CI（见 `.github/workflows/ci.yml`），"改了源码却忘记重新生成"就再也不会被合并进去。

### 2.8 跨后端验证

CLI 的标记解析、文件读写与 `check` 在 `js` 与 `wasm-gc` 两个后端行为一致：

```bash
$ moon run cmd/main --target wasm-gc -- check examples
moonforge: 已扫描 2 个源文件，生成物与源文件一致，无漂移
```

唯一的跨后端差异在**出错路径**：`js` 后端能干净地返回非零退出码；`wasm-gc` 没有标准的退出原语，友好提示行会先打印，随后附带一段 `RuntimeError: unreachable` 回溯。因此 CI 中的漂移检查固定使用默认的 `js` 后端（见 `.github/workflows/ci.yml`）。

## 3. 扩展一条新规则

演示"可扩展"不是口号。最有说服力的一步是**不改 MoonForge 任何一行源码**：

```bash
$ moon test --target js          # 其中包含 examples/extension/tocsv_wbtest.mbt 的 5 条用例
```

`examples/extension/` 扮演一个"下游使用者"：它自己定义目标 trait（`ToCsv`）、
标记 trait（`DeriveToCsv`）、规则（`ToCsvRule`），再把内置规则与自己的规则
合成一个新集合交给 `generate(...)`。`tocsv_wbtest.mbt` 断言了四件事：

| 断言 | 证明了什么 |
|---|---|
| 标记 → 生成物中确实出现 `pub impl @ext.ToCsv for Row with fn to_csv(self) { ... }` | 第三方规则**真的生效** |
| 生成物复用用户写的包前缀 `@ext` | 工具不会改写你的别名 |
| 并集里内置规则与第三方规则共存，顺序 = 源码书写顺序 | 规则集是**可组合**的 |
| 只传自己的规则时，内置标记被报"未知标记 trait" | 规则集是**可替换**的，不是写死的常量 |

完整步骤见 [`扩展规则指南.md`](扩展规则指南.md)，浓缩版：

1. 定义目标 trait 与标记 trait（或复用 `moonforge/derive` 里的）；
2. 新建一个规则类型，写两个 `impl @forge.DeriveRule for <你的规则>` 块
   （一个 `head()` 提供身份，一个 `generate()` 提供生成逻辑）；
3. 把自己的规则并进 `Array[&@forge.DeriveRule]`，传给 `@forge.generate(...)`；
4. 补一组用例（正例 + 不适用 + 白名单外跳过 + 前缀复用）。

**不需要修改词法、语法、代码生成等任何核心代码。**

想动手试试的话，有一个天然的练习题：把 `to_pairs` 改造成 `to_json`——它不是简单换个名字，因为
"如何把 `Int` / `Bool` / 嵌套类型转成 JSON 字面量"必须由规则自己决定；这正是本项目
"规则是一等公民"设计的价值所在。`to_pairs` 本身就是按这套流程加进来的第 4 条规则。

## 4. 生成物的列宽预算（这一轮新加的一条硬约束）

第 1 节的第 4 阶段会跑 `scripts/fmt_budget_probe.sh`，它做的是**实测**而不是估计：

```
OK: 列宽预算 82 实测成立（4 条里 4 条折开）
OK: 预算内不折行、超预算折开，两个方向都成立
```

为什么要在意：`moonfmt` 会把超过 **82 列**的 `impl` 头折开（83 列起）。
生成物是提交进仓库的，用户迟早会跑 `moon fmt` —— 一旦生成器的字节与格式化结果不同，
`check` 就永久报漂移，而且 `gen` 也治不好（它照旧写单行版）。

所以生成的 impl 头**不写返回类型**（返回类型由目标 trait 声明唯一决定），
把这一行从 83～85 列降到 58～61 列，留出约 20 列余量。真的超了（类型名 ≳ 21 列）
会在生成阶段给出可操作的诊断，而不是让你在 `moon fmt` 与 `check` 之间反复横跳。

这条边界由 `scripts/fmt_budget_probe.sh` 用**真实 `moonfmt`** 现场量、并在量不到预期时非零退出。

## 5. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `moon check` 报 `Cannot load the core file` | 工具链安装不完整，重新执行官方安装脚本 |
| `moon run` 报找不到命令 | 未把 `$HOME/.moon/bin`（Windows 为 `%USERPROFILE%\.moon\bin`）加入 `PATH` |
| `moon check` 报 `unknown trait @derive.DeriveXxx` | 标记 trait 名写错（最常见的错是写了**规则键** `field_names` 而不是标记名 `DeriveFieldNames`）。跑 `list-rules` 看四个身份字段 |
| 报 `Invalid grouped impl declarations` | 标记 impl 写成了空块。标记 trait 必须带一个方法，所以合法写法是 `with fn requested(_self) {}` |
| `moon fmt --check` 失败 | 仓库里有未格式化的文件，跑一次 `moon fmt` 并提交。注意它有差异时给的是**非零**退出码（本机实测为 `127`，不是 `1`） |
| `check` 报漂移但我没改源码 | 先确认生成物**已提交**（不要写进 `.gitignore`）。CRLF/LF 差异**不会**造成误报——读取时会先归一化换行符；`scripts/e2e.sh` 第 5 阶段固化了这条 |
| `gen` 报"impl 头超过 `moon fmt` 的列宽预算" | 类型名太长（≳ 21 列）。缩短类型名、给包起更短的别名，或缩短规则的成员签名——见第 4 节 |
| `explain` 里看不到我的标记 | 标记必须像上面那样写成本文件内的 `impl <前缀>.<标记> for <类型>`；**跨文件不生效**（标记要写在类型所在文件） |
| 规则报"未知的标记 trait" | 标记名拼写正确但没注册；用 `list-rules` 核对，或确认你的扩展规则已并进规则集合 |
| 规则报"不适用" | 该类型没有具名字段（enum / 位置参数结构体 / 没写字段体）。加标记是安全的，不会报错也不会产出错误代码 |
| `explain` 报"找不到路径"/"是目录" | `explain` 只接受**单个 `.mbt` 文件**，不能传目录或规则名；正确用法 `moon run cmd/main -- explain examples/models.mbt` |
| 想在脚本里判断结果 | 看退出码：`0` 成功 / `1` 检出漂移 / `2` 参数或路径有误 |
