# 可复现演示说明 · MoonForge

> 目标：让评委在一台装有 MoonBit 工具链的机器上，**5 分钟内**完整复现从"写类型定义"到"生成代码被编译器验证"的全过程，并亲手看到漂移检查拦住一次错误提交。

## 2. 分步演示（讲清楚每一环在做什么）

### 2.1 看工具认识哪些规则

```bash
$ moon run cmd/main -- list-rules
已注册的派生规则（用法：在类型的 doc comment 里写 `@derive(<规则名>)`）：

  field_names
      为 struct 生成 T::field_names() -> Array[String]，顺序与字段声明一致
  validate
      ...
```

### 2.2 看一份真实的输入

打开 `examples/models.mbt`。它就是**普通 MoonBit 代码**，没有任何新语法：

```moonbit
/// 用户信息。
///
/// @derive(validate, diff, field_names)
pub(all) struct User {
  /// 姓名
  /// @nonempty
  name : String

  /// 年龄
  /// @min(0) @max(150)
  age : Int

  /// 电子邮箱 —— 没有校验注解，因此不会产生任何检查代码
  email : String
} derive(Eq, Debug)
```

### 2.3 看解析结果（工具"能解释自己"）

```bash
$ moon run cmd/main -- explain examples/models.mbt
moonforge explain: examples/models.mbt

  struct User   (line 13)
    doc: 用户信息。
    @derive(validate, diff, field_names)
      [ok] validate 会生成代码
      [ok] diff 会生成代码
      [ok] field_names 会生成代码
    field name : String @nonempty
    field age : Int @min(0) @max(150)
    field email : String
  ...
```

重点看 `Order.quantity`：它写了 `@nonempty` 但类型是 `Int`，工具会**跳过而不是硬塞检查**，并在生成文件里留下说明行。

### 2.4 生成

```bash
$ moon run cmd/main -- gen examples
  generated examples/models_derive_gen.mbt  [User.validate, User.diff, User.field_names, Order.field_names, Order.validate, Order.diff]

moonforge: 扫描 2 个源文件，生成 1 个文件，警告 0 条
```

打开 `examples/models_derive_gen.mbt` 查看生成结果，注意：

- 文件头写明来源与重现命令；
- 说明行 `// moonforge: 跳过 Order.quantity ...` 解释了"为什么不生成"；
- **生成方法在仓库里没有任何手写实现**。

### 2.5 关键一步：让编译器来裁决

生成物是**提交进仓库**的，所以它一直在参与编译：

```bash
$ moon check
Finished. moon: ran N tasks, now up to date   # N 随缓存状态变化，关键是 "now up to date"
```

**反证**：把生成文件删掉/改坏，`moon check` 会立刻失败——说明编译检查确实覆盖了生成代码。

```bash
$ rm examples/models_derive_gen.mbt && moon check   # 失败
$ moon run cmd/main -- gen examples && moon check   # 恢复
```

### 2.6 让生成代码真跑起来

`examples/models_wbtest.mbt` 里的测试**直接调用自动生成的方法**：

```moonbit
@debug.debug_inspect(u.validate(), content="Err(\"User.name must not be empty\")")
@debug.debug_inspect(a.diff(b), content="[\"age\"]")
```

```bash
$ moon test --target js
Total tests: 62, passed: 62, failed: 0
```

### 2.7 演示漂移检查（CI 的核心价值）

```bash
# 改动源文件但故意不重新生成
$ printf '\n///\n/// @derive(field_names)\nstruct DriftProbe {\n  k : String\n}\n' >> examples/models.mbt

$ moon run cmd/main -- check examples
  [drift] 内容过期：examples/models_derive_gen.mbt

moonforge: 检测到 1 处生成物漂移（已扫描 2 个文件）。
请运行 `moon run cmd/main -- gen <dir>` 重新生成并提交。
$ echo $?
1

# 重新生成后恢复
$ moon run cmd/main -- gen examples
$ moon run cmd/main -- check examples
moonforge: 已扫描 2 个源文件，生成物与源文件一致，无漂移
```

（这与 `scripts/e2e.sh` 的第 4 阶段是同一套动作；脚本里用 `trap` 保证演示后自动还原源文件。）

退出码约定：`0` 成功；`1` 检出漂移；`2` 参数或路径有误。任何错误都会落成**一行** `moonforge: ...` 提示，不会把运行期堆栈喷进 CI 日志。

把 `check` 接进 CI（见 `.github/workflows/ci.yml`），"改了源码却忘记重新生成"就再也不会被合并进去。

### 2.8 跨后端验证

CLI 的 `@derive` 解析、文件读写与 `check` 在 `js` 与 `wasm-gc` 两个后端行为一致：

```bash
$ moon run cmd/main --target wasm-gc -- check examples
moonforge: 已扫描 2 个源文件，生成物与源文件一致，无漂移
```

唯一的跨后端差异在**出错路径**：`js` 后端能干净地返回非零退出码；`wasm-gc` 没有标准的退出原语，友好提示行会先打印，随后附带一段 `RuntimeError: unreachable` 回溯。因此 CI 中的漂移检查固定使用默认的 `js` 后端（见 `.github/workflows/ci.yml`）。

## 3. 扩展一条新规则（约 5 分钟）

演示"可扩展"不是口号：

1. 新建 `rules/to_pairs.mbt`，写一个返回 `@forge.Rule` 的公开函数（参考 `rules/field_names.mbt`，约 20 行）；
2. 在 `rules/registry.mbt` 的 `all()` 数组里加一项；
3. 在 `rules/rules_wbtest.mbt` 补一组用例；
4. `moon test --target js` 通过即完成。

**不需要修改词法、语法、代码生成等任何核心代码。**

## 4. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `moon check` 报 `Cannot load the core file` | 工具链安装不完整，重新执行官方安装脚本 |
| `moon run` 报找不到命令 | 未把 `$HOME/.moon/bin` 加入 `PATH` |
| `check` 报漂移但我没改源码 | 换行符（CRLF/LF）差异会算作漂移；用 `git config core.autocrlf false` 并统一 LF |
| `explain` 里看不到我的 `@derive` | doc comment 与声明之间有空行；注释必须**紧邻**声明 |
| 规则报"未注册" | 规则名写错；用 `list-rules` 核对（需小写字母/数字/下划线） |
| `explain` 报"找不到路径"/"是目录" | `explain` 只接受**单个 `.mbt` 文件**，不能传目录或规则名；正确用法 `moon run cmd/main -- explain examples/models.mbt` |
| 想在脚本里判断结果 | 看退出码：`0` 成功 / `1` 检出漂移 / `2` 参数或路径有误 |
