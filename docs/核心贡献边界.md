# 独立核心贡献边界 · MoonForge

> 这一页只回答一个问题：**这个项目里，哪一部分是"只能由它提供"的？**
> 评审意见指出"已有 parser、MoonMacro、codegen 可复用，申报剩余主要为少量模板与生成物管理"。
> 这个判断在事实层面是对的 —— 所以这一页不辩解，而是把边界划清楚：
> 哪些部分**确实不该算贡献**，哪一部分**是**。

---

## 1. 先把不该算贡献的部分摘出去

| 能力 | 现状 | 本项目的态度 |
|---|---|---|
| 解析 MoonBit 源码 | 官方有 `moonc`；社区有 [tree-sitter-moonbit](https://github.com/moonbitlang/tree-sitter-moonbit)（含 quotation 扩展） | **不算贡献。** 本项目的 `lexer.mbt` / `parser.mbt`（约 780 行）只是**前端适配层**：为了端到端能跑、为了不引入依赖而自带的一个子集实现。它随时可以被换掉 |
| 宏 / 模板展开 | [MoonMacro](https://mooncakes.io/docs/faaaaa3/moonmacro)（`faaaaaa3/moonmacro`）已提供 `macro_rules!`、`#[macro_derive]` 与 13 个内置宏 | **不算贡献。** 拼文本谁都会；"我写了一个模板引擎"不是理由 |
| 生成代码（字符串拼接） | 同上，以及任何 codegen 库 | **不算贡献。** 生成本身没有壁垒 |
| 生成物落盘 / 清理 / 版本戳 | 任何"生成器"都会做 | **不够。** 这部分确实不构成独立贡献，只是必要工程 |

**如果只看上面四行，这个项目确实只剩"少量模板 + 生成物管理"。** 评审的判断成立。

---

## 2. 那什么是这一层给不了的

上面这些组件的共同点是：**它们把"输入"当作文本，把"输出"当作文本。**
中间没有"这个类型长什么样、这条规则能不能对它生成、生成出来会不会破坏工具链"的位置。

MoonForge 的独立贡献就是补上这个位置 —— 把它定义为**三份可被复核的契约**：

| 契约 | 内容 | 谁来复核 |
|---|---|---|
| **入口契约** | 派生请求是一行**真实的 trait impl**，不是注释、不是私有 DSL | `moon check`（拼错标记名 → 编译期报 unknown trait） |
| **输入契约** | 规则只能看到 `DeriveInput`：类型名、字段体形态、**归一化后的**字段（名 / 类型原文 / 注解）、触发它的请求 | 契约测试（`derive_input_wbtest.mbt` 6 条） |
| **输出契约** | 规则只能返回 `Fragment`：说明行 + 成员体，且成员体**不写返回类型** | 三个裁判：`moon check` 编译、`moon fmt` 逐字节一致、`check` 子命令比对漂移 |

一句话概括：

> **MoonForge 的贡献不是"能生成代码"，而是"让生成出来的代码可以被编译器、格式化器、
> CI 三个裁判同时复核，并让第三方在不改内核的前提下接入这套复核"。**

这句话可以被检验，因为它由三个结构性事实支撑（下一节）。

---

## 3. 三个结构性事实（不是形容词）

### 3.1 parser 是可替换的 —— 有测试直接证明

规则只吃 `DeriveInput`，看不到 `TypeDef`。`rules/rules_wbtest.mbt` 里有一条测试
**完全不经过 parser**，手工构造一个 `DeriveInput` 字面量，直接调用规则并断言生成结果：

```moonbit
test "前端无关：手工构造 DeriveInput（完全不经过 parser）也能生成" {
  let input : @forge.DeriveInput = {
    type_name: "Row",
    body: @forge.Record,
    fields: [
      { name: "id", ty: "String", doc: "", attrs: [], line: 2 },
      { name: "n", ty: "Int", doc: "", attrs: [], line: 3 },
    ],
    request: { prefix: "@d", marker: "DeriveFieldNames", line: 1 },
  }
  ...
}
```

这条测试的意思是：**换掉整个前端，规则一条都不用改。**
换句话说，那 780 行 parser 是"用完即弃的适配层"，不是核心。

### 3.2 规则是可替换的 —— 有不改内核的第三方样例

`examples/extension/` 自带目标 trait（`ToCsv`）、标记 trait（`DeriveToCsv`）、规则
（`ToCsvRule`），把内置规则与自己的规则合成新集合后直接生成，**没有修改
moonforge 的任何源码**，`tocsv_wbtest.mbt` 用 5 条用例把它钉住。

### 3.3 生成物是格式化器的**固定点** —— 有实测脚本

`scripts/fmt_budget_probe.sh` 用真实 `moonfmt` 现场构造预算两侧的 `impl` 头，
断言"≤ 82 列保持、≥ 83 列折开"；`examples/models_derive_gen.mbt` 与 `moonfmt`
的输出**逐字节相同**。

这一条不是洁癖：生成物是提交进仓库的，用户迟早会跑 `moon fmt`。
生成器字节一旦与格式化结果不同，`check` 就**永久**报漂移，而且 `gen` 也治不好。
所以"输出是 fmt 的固定点"必须被当作契约来守，而不能靠"大概差不多"。

## 4. 与 MoonMacro 的分工（最容易被拿来对比的一个）

不回避：MoonMacro 的 `#[macro_derive]` 在**目标**上和本项目最接近。差别在**输入**：

| | MoonMacro | MoonForge |
|---|---|---|
| 输入形态 | 纯文本（其文档自述"不依赖 MoonBit 解析器或 AST"） | **结构化字段模型**（字段名 / 归一化类型原文 / 注解 / 字段体形态） |
| 能不能"按字段类型决定" | 不能：只知道文本长什么样 | 能：`f.ty == "String"` 这种判断成立，所以 `@nonempty` 只对 `String` 生效 |
| 能不能"拒绝生成" | 没有这个概念：宏要么展开要么不展开 | **能**：规则返回 `None` = 不适用，生成器把它翻译成带行号的诊断 |
| 入口的可校验性 | 预处理阶段的私有属性 | 真实 `impl`，`moon check` 编译期校验 |
| 生成物治理 | 不是它的定位 | 字节稳定 + fmt 固定点 + 版本戳 + 漂移检测 |
| 定位 | 通用文本宏系统 | **结构化派生契约 + 生成物治理** |

两者不是替代关系：MoonForge 的生成物是普通 `.mbt`，完全可以再交给 MoonMacro 处理。

## 5. 消融实验：删掉哪一层，项目就没了

这是判断"什么是核心"最干脆的办法。

| 删掉 | 后果 | 结论 |
|---|---|---|
| 删掉 `parser.mbt` / `lexer.mbt` | 手工构造 `DeriveInput` 仍可生成（3.1 的测试）；只是不能再从 `.mbt` 直接读 | **前端不是核心** |
| 删掉 `rules/` 四条内置规则 | 契约、生成器、CI 闭环都还在；换成第三方规则集照样跑 | 规则是**内容**，不是核心 |
| 删掉 `derive_input.mbt` + `rule.mbt` 的契约 | 规则只能退回"拿一段字符串去拼"，`None`/白名单/fmt 固定点全部失效 → 退化成"少量模板" | **这一层是核心** |
| 删掉 fmt 固定点与漂移检查 | 生成物进仓库这条路线立刻崩掉（用户 fmt 一次就永久红） | **治理是核心的一部分** |

## 6. 可复现的证据清单

```bash
moon test --target js                      # 126 个用例；其中 7 条是契约/前端无关性测试
moon check                                 # 入口契约：标记 impl 被真实编译
bash scripts/e2e.sh                        # 6 阶段：漂移 / 测试 / 真编译 / fmt 固定点 / CRLF / 退出码
bash scripts/fmt_budget_probe.sh           # 生成物列宽预算：用真实 moonfmt 实测
```

| 主张 | 复现命令 | 期望 |
|---|---|---|
| 前端可替换 | `moon test --target js` | "前端无关"用例通过 |
| 规则可替换（不改内核） | `moon test --target js` | `examples/extension` 5 条用例通过 |
| 输出是 fmt 的固定点 | `bash scripts/e2e.sh` | 第 4 阶段通过 |
| 输入契约成立 | `moon test --target js` | `derive_input_wbtest.mbt` 6 条通过 |
| 生成代码由编译器裁决 | `rm examples/models_derive_gen.mbt && moon check` | 失败；`gen` 后恢复 |

## 7. 这一页之后，申报材料的口径

- `项目申报书.md` 的"独立核心贡献"一节直接引用本页第 2 / 3 节；
- README 第 1 节与第 7 节按"契约层"而不是"解析器"来介绍项目；
- `docs/扩展规则指南.md` 从"输入契约"讲起，而不是从"怎么写模板"讲起。

**一句话版本**：解析器是别人的，生成代码谁都会；本项目的独立贡献是把"派生"
定义成三份契约，并证明这三份契约能被编译器、格式化器、CI 同时复核。
