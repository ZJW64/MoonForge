# 扩展规则指南 · MoonForge

> 目标：读完这一页，你能在 **15 分钟**内给 MoonForge 加一条自己的派生规则 ——
> 而且**不需要改动 MoonForge 的任何一行代码**。
> 本指南以 `examples/extension/tocsv.mbt`（第三方规则 `to_csv`）为完整样例。

## 0. 派生这件事由三段构成

先看清结构，后面每一步都只是填其中一段：

| 段 | 是什么 | 谁来写 |
|---|---|---|
| **目标 trait** | "能做什么"。例如 `trait ToCsv { fn to_csv(Self) -> String }` | 你（或复用 `moonforge/derive` 里的内置目标 trait） |
| **标记 trait** | "这个类型请求了这次派生"。例如 `trait DeriveToCsv { fn requested(Self) -> Unit }` | 你（或复用内置标记 trait） |
| **规则** | "怎么从类型定义生成实现"。实现 `@forge.DeriveRule` | 你 |

用户在类型所在文件里写一行

```moonbit
pub impl @ext.DeriveToCsv for Row with fn requested(_self) {}
```

于是"请求"变成一条**语言层面**的事实：`moon check` 能编译它，MoonForge 能读到它，
别的工具也能读到它。**MoonForge 不发明语法**。

> 两个容易踩的点：
> ① 标记 trait 必须带至少一个方法 —— MoonBit 不允许 `impl T for X {}` 这种空块
> （报 `Invalid grouped impl declarations`），所以用 `fn requested(Self) -> Unit` + 空方法体；
> ② 入口**不能用 `derive(...)`** —— 编译器的 `derive(...)` 只认内置 trait 白名单，
> 遇到自定义 trait 直接报 `Don't know how to derive trait X`（E4077）。
> 用普通 `impl` 才没有这个限制。

## 1. 规则的契约

一条规则就是一个 `@forge.DeriveRule` 的实现：

```moonbit
pub(open) trait DeriveRule {
  /// 规则的静态身份：规则键 / 标记名 / 目标 trait 名 / 描述
  fn head(Self) -> RuleHead
  /// 生成 `impl` 的成员体。None = 该规则不适用于这个类型
  fn generate(Self, TypeDef) -> Fragment?
}
```

`RuleHead` 的四个字段都有明确位置：

| 字段 | 含义 | 用在哪 |
|---|---|---|
| `key` | 规则键（小写字母 / 数字 / 下划线） | `list-rules` 展示、诊断文案 |
| `marker` | **标记 trait 名**（如 `DeriveToCsv`） | 用户写的那行 `impl` 靠它匹配 |
| `trait_name` | **生成的 impl 的目标 trait 名**（如 `ToCsv`） | 拼 `pub impl <前缀>.<trait_name> for <类型>` |
| `description` | 一句话说明 | `list-rules` |

> 为什么 SPI 只有两个方法？因为 MoonBit 里一个 `impl ... with` 块**只能放一个方法**，
> 每个方法都要写一个独立的 `impl` 块。把身份字段收进 `head()` 返回的结构体，
> 规则作者只需写两个 `impl` 块，而不是七个。需要单独取某个字段时用现成的读取函数：
> `@forge.key_of(r)` / `marker_of(r)` / `trait_name_of(r)` / `description_of(r)`。

四条硬约束，违反任何一条都会让工具的质量下降：

| 约束 | 为什么 |
|---|---|
| **纯函数**：同一个 `TypeDef` 必须产出同样的字符串 | 生成物要字节稳定才能进版本库、才能被 `check` 比对。不要读取文件、时间、随机数 |
| **`None` 表示"不适用"，不是"失败"** | 一条规则不适用于某个类型是**正常情况**。抛错会让整次 `gen` 中断，其他类型也生成不了 |
| **`impl_body` 不写返回类型** | 返回类型由目标 trait 的声明唯一决定。抄一遍既重复，又会撑爆 `moon fmt` 的列宽预算 → 生成物与格式化结果不一致、`check` 永久报漂移（见第 3 节） |
| **不确定就跳过，并留一行 `// moonforge:` 说明** | 生成代码必须能过 `moon check`。"为什么不生成"和"生成了什么"一样是产品的一部分 |

## 2. 三件事：写文件 / 注册 / 补测试

### 2.1 新建 `rules/<规则名>.mbt`（或在**你自己的包**里）

```moonbit
// 规则类型：普通 struct，可以是空的
pub struct ToJsonRule {}

///|
pub impl @forge.DeriveRule for ToJsonRule with fn head(_self) -> @forge.RuleHead {
  {
    key: "to_json",
    marker: "DeriveToJson",
    trait_name: "ToJson",
    description: "为 struct 实现 ToJson::to_json",
  }
}

///|
pub impl @forge.DeriveRule for ToJsonRule with fn generate(_self, td) -> @forge.Fragment? {
  // 1) 先做前置判断：没有具名字段的类型直接放弃
  if !td.has_named_fields() {
    return None
  }
  // 2) 逐字段决定"生成什么"和"为什么要跳过"，分别进 impl_body 与 notes
  // 3) 用 Fragment 返回，交给生成器拼装
  ...
  Some({ notes, impl_body: b.to_string() })
}
```

规则键只允许**小写字母、数字、下划线**（`is_valid_rule_name` 在 `rule.mbt` 里校验；
不合法时用户拿到的是一句"名字不合法"，而不是笼统的"未知规则"）。

### 2.2 把规则并进集合

```moonbit
pub fn all() -> Array[&@forge.DeriveRule] {
  [
    FieldNamesRule::{ } as &@forge.DeriveRule,
    ValidateRule::{ } as &@forge.DeriveRule,
    DiffRule::{ } as &@forge.DeriveRule,
    ToPairsRule::{ } as &@forge.DeriveRule,
    ToJsonRule::{ } as &@forge.DeriveRule,   // ← 加这一项
  ]
}
```

**关键点：集合是显式传入 `@forge.generate(...)` 的普通值，不是工具内部的常量。**
因此第三方可以这样用（不需要 fork 本仓库、不需要往注册表里塞东西）：

```moonbit
pub fn rules_with_extension() -> Array[&@forge.DeriveRule] {
  let out : Array[&@forge.DeriveRule] = []
  for r in @rules.all() {
    out.push(r)                        // 内置四条
  }
  out.push(ToCsvRule::{ } as &@forge.DeriveRule)   // 自己的
  out
}
```

`Array[&DeriveRule]` 是**异构的 trait 对象数组** —— 遍历时只调 trait 方法，
不关心背后是什么具体类型。这正是"规则数量可以增长"的技术前提。

### 2.3 补一组用例

每条规则**至少**三类用例：

```moonbit
test "to_json/正例"    // 有具名字段 → 断言生成的文本
test "to_json/不适用"  // enum、struct Point(Int, Int) → 断言返回 None
test "to_json/跳过"    // 白名单外类型 → 断言说明行存在
```

`examples/extension/tocsv_wbtest.mbt` 还多覆盖了两条只属于"第三方"的用例：

```moonbit
test "第三方规则：不改 moonforge 源码即可注册并生效"        // 端到端：标记 → 生成物
test "只用自己的规则集：内置规则完全不出场"                // 规则集合确实被替换掉了
```

## 3. 必须用对的 API

IR 只有这几个入口，别绕过它们去改词法/语法代码。

### `TypeDef::has_named_fields()` —— 唯一的前置判断

**不要**写 `if td.is_enum() { return None }`。位置参数结构体 `struct Point(Int, Int)`
在类型种类上仍是 struct，但它没有字段名。用 `has_named_fields()` 才能同时挡住
"枚举"和"位置参数结构体"，而且将来 IR 新增字段体形态时**不需要改规则**。

```moonbit
if !td.has_named_fields() {
  return None    // 让工具打印"不适用 + 原因"，而不是生成一个语义错误的空实现
}
```

### `Fragment { notes, impl_body }` —— 两半各司其职

```moonbit
pub(all) struct Fragment {
  notes : Array[String]      // 前置说明行，每行自带换行；无跳过项时为空数组
  impl_body : String         // `impl ... with` 之后的成员文本（以 `fn` 开头）
}
```

分两半不是设计癖好：说明行是 `// moonforge:` 注释，必须落在 `impl` **之前**、
且与 `impl` 之间**空一行**（`moon fmt` 对"独立注释块 + 紧随其后的 item"的要求）；
而成员体要接在 `with` 之后。两者由生成器分别摆放，规则不需要知道排版细节。

### 成员体只写 `fn <方法名>(<参数>) {`，**不要抄返回类型**

```moonbit
// ✅ 对：返回类型由 trait 声明决定
b.write_string("fn to_pairs(self) {\n")

// ❌ 错：抄上返回类型会把 impl 头撑到 83 列以上
b.write_string("fn to_pairs(self) -> Array[(String, String)] {\n")
```

生成器会拼出 `pub impl <前缀>.<Trait> for <类型> with fn ... {`。
抄上返回类型后这一行达 83～85 列，而 **`moonfmt` 对 82 列及以下的行保持原样、
83 列起会把返回类型或参数表折开** → 生成物与格式化结果不一致 → 用户跑一次
`moon fmt`，`check` 就永久报漂移，而且 `gen` 也治不好（它照旧写单行版）。

不抄返回类型后 impl 头是 58～61 列，留出约 20 列余量给类型名与方法名。
真的超了（类型名 ≳ 21 列）不会静默：生成阶段会给出可操作的诊断，
提示你缩短类型名、给包起更短的别名、或缩短方法签名。
这条边界由 `scripts/fmt_budget_probe.sh` 用**真实 `moonfmt`** 现场实测钉住。

### `FieldDef` 与白名单判断

- `td.fields` 拿到字段，`f.name` 是字段名，`f.ty` 是**源码原文**（如 `Array[Int]`、`Int?`）；
- 类型比较一律走**白名单**（`is_numeric_type` 或 `f.ty == "String"`），不要做字符串前缀猜测；
- 字段注解用 `f.attr_args("min")` 取参数、`f.has_attr("nonempty")` 查有无。

## 4. 允许生成什么：白名单纪律

这是本项目最容易踩、也最值得讲的一条。

生成物是要**提交进仓库、被 `moon check` 真实编译**的。所以"生成一段编译不过的代码"
是**最严重的 bug**——比"少生成一段代码"严重得多：后者只是功能缺失，前者会让整个项目构建失败。

因此对所有需要"类型能力"的规则（比较、转字符串、序列化），纪律是：

> **只对确定的类型生成；不确定就跳过，并在生成文件里写清原因。**

判断"确定"的依据是**类型名原文的白名单**，而不是推断：

| 需要的能力 | 白名单 | 例 |
|---|---|---|
| 可比较（`!=`） | 由 `diff` 的规则描述声明"字段类型需实现 `Eq`"，节点在 `moon check` 阶段暴露 | `diff` |
| 可 `== ""` | 仅 `String` | `validate` 的 `@nonempty` |
| 可 `<= 0` / `< n` / `> n` | `is_numeric_type` 的 8 个内建数值类型 | `validate` 的 `@positive` / `@min` / `@max` |
| 可当字符串用 | 仅 `String` | `to_pairs` / `to_csv` |

一个反面例子（**不要这样做**）：为了让 `to_pairs` 覆盖 `Int` 字段，写成

```moonbit
// ❌ 错：字段类型未必实现 Debug，生成物编译不过
pairs.push("(\"" + f.name + "\", @debug.to_string(self." + f.name + "))")
```

正确做法是跳过 + 说明行：

```moonbit
// ✅ 对：Int 该怎么变成字符串是语义问题，工具不替用户决定
notes.push("// moonforge: 跳过 " + td.name + "." + f.name + " 的 to_pairs（类型 " + f.ty + " 不是 String；如何转成字符串由使用者决定）\n")
```

## 5. 完整样例：`ToCsvRule`（逐段讲解）

`examples/extension/tocsv.mbt` 是一个**完整可运行**的第三方扩展，同样约 30 行：

```moonbit
// ① 目标 trait 与标记 trait：都由扩展方定义
pub(open) trait ToCsv {
  fn to_csv(Self) -> String
}

pub(open) trait DeriveToCsv {
  fn requested(Self) -> Unit
}

// ② 规则身份
pub struct ToCsvRule {}

pub impl @forge.DeriveRule for ToCsvRule with fn head(_self) -> @forge.RuleHead {
  {
    key: "to_csv",
    marker: "DeriveToCsv",
    trait_name: "ToCsv",
    description: "把 struct 的 String 字段渲染成一行 CSV（第三方规则示例）",
  }
}

// ③ 生成逻辑
pub impl @forge.DeriveRule for ToCsvRule with fn generate(_self, td) -> @forge.Fragment? {
  if !td.has_named_fields() {               // ← 前置判断
    return None
  }
  let cells : Array[String] = []
  let notes : Array[String] = []
  for f in td.fields {
    if f.ty == "String" {                   // ← 白名单
      cells.push("self." + f.name)
    } else {
      notes.push("// moonforge: 跳过 ...\n")   // ← 说明行
    }
  }
  let b = StringBuilder()
  b.write_string("fn to_csv(self) {\n")     // ← 不写返回类型
  b.write_string("  [" + cells.join(", ") + "].join(\",\")\n")
  b.write_string("}\n")
  Some({ notes, impl_body: b.to_string() })
}
```

用户在 `Row` 上写一行标记，生成器就产出（`tocsv_wbtest.mbt` 的实际断言）：

```moonbit
// 输入（源文件里）
pub impl @ext.DeriveToCsv for Row with fn requested(_self) {}

// 输出（生成物里，注释行来自"跳过 Int 字段"的说明）
// moonforge: 跳过 Row.n 的 to_csv（类型 Int 不是 String）

///|
pub impl @ext.ToCsv for Row with fn to_csv(self) {
  [self.a].join(",")
}
```

注意两点：

- 生成的 impl 头用的是**用户写标记时的包前缀** `@ext`，而不是内置的 `@derive`
  —— 你给包起什么别名，工具就复用那个别名；
- `///|` 这一行由**生成器**负责写（MoonBit 要求顶层 `impl` 前面有 `///|`），
  规则只提供成员体。

## 6. 收尾检查清单

新规则提 PR 之前，跑一遍：

```bash
moon run cmd/main -- list-rules       # 1. 新规则出现在列表里，四个身份字段都对
moon run cmd/main -- gen examples     # 2. 有输入能触发它，生成物符合预期
moon check                            # 3. 生成物真的能编译（最关键）
moon fmt --check                      # 4. 仓库已格式化
moon run cmd/main -- check examples   # 5. 生成物与源文件一致（无漂移）
moon test --target js                 # 6. 三类用例都过
bash scripts/e2e.sh                   # 7. 端到端 6 个阶段全过
```

第 3 步与第 4 步是**很多人会漏掉的两步**：

- 第 3 步：`gen` 成功不等于生成物正确。只有 `moon check` 编译过，才证明它是合法 MoonBit；
- 第 4 步：生成物要与 `moon fmt` 的输出**字节一致**。否则用户格式化一次，`check` 就永久报漂移。
  这也是"成员体不写返回类型"的由来 —— 详见第 3 节。

把新规则的输出补进 `examples/`（输入 + 生成物一起提交），并在 `CHANGELOG.md`
最新版本段记一条，这样 `check` 和 CI 会持续帮你看住它。
