# 扩展规则指南 · MoonForge

> 目标：读完这一页，你能在 **15 分钟**内给 MoonForge 加一条自己的派生规则，并且知道
> "什么样的代码才允许被生成"。本指南以 `to_pairs`（本仓库第 4 条规则）为完整样例。

## 0. 规则的契约

一条规则就是一个 `@forge.Rule` 值：

```moonbit
pub(all) struct Rule {
  name : String
  description : String
  gen : (TypeDef) -> String?      // None = 该规则不适用于这个类型
}
```

三条硬约束，违反任何一条都会让工具的质量下降：

| 约束 | 为什么 |
|---|---|
| **纯函数**：同一个 `TypeDef` 必须产出同样的字符串 | 生成物要字节稳定才能进版本库、才能被 `check` 比对。不要读取文件、时间、随机数 |
| **`None` 表示"不适用"，不是"失败"** | 一条规则不适用于某个类型是**正常情况**。抛错会让整次 `gen` 中断，其他类型也生成不了 |
| **不确定就跳过，并留一行 `// moonforge:` 说明** | 生成代码必须能过 `moon check`。"为什么不生成"和"生成了什么"一样是产品的一部分 |

## 1. 三件事：写文件 / 注册 / 补测试

### 1.1 新建 `rules/<规则名>.mbt`

规则名只允许**小写字母、数字、下划线**（`is_valid_rule_name` 在 `rule.mbt` 里校验；
不合法时用户拿到的是一句"名字不合法"，而不是笼统的"未知规则"）。

```moonbit
// rules/to_json.mbt
///|
pub fn to_json() -> @forge.Rule {
  {
    name: "to_json",
    description: "为 struct 生成 T::to_json(self) -> String",
    gen: fn(td : @forge.TypeDef) -> String? {
      // 1) 先做前置判断：没有具名字段的类型直接放弃
      if !td.has_named_fields() {
        return None
      }
      // 2) 逐字段决定"生成什么"和"为什么要跳过"
      // 3) 组装文本，返回 Some(...)
      ...
    },
  }
}
```

### 1.2 在 `rules/registry.mbt` 注册

```moonbit
pub fn all() -> Array[@forge.Rule] {
  [field_names(), validate(), diff(), to_pairs(), to_json()]
}
```

数组顺序 = `moonforge list-rules` 的展示顺序。

### 1.3 在 `rules/rules_wbtest.mbt` 补一组用例

每条规则**至少**三类用例：

```moonbit
test "to_json/正例"    // 有具名字段 → 断言生成文本
test "to_json/不适用"  // enum、struct Point(Int, Int) → 断言 gen 返回 None
test "to_json/跳过"    // 白名单外类型 → 断言说明行存在
```

## 2. 三个必须用对的 API

IR 只有这几个入口，别绕过它们去改词法/语法代码。

### `TypeDef::has_named_fields()` —— 唯一的前置判断

**不要**写 `if td.is_enum() { return None }`。位置参数结构体 `struct Point(Int, Int)`
在 `TypeKind` 上是 `TStruct`，但它没有字段名。用 `has_named_fields()` 才能同时挡住
"枚举"和"位置参数结构体"，而且将来 IR 新增字段体形态（比如 `newtype`）时**不需要改规则**。

```moonbit
if !td.has_named_fields() {
  return None    // 让工具打印"不适用 + 原因"，而不是生成 field_names() { [] }
}
```

### `@forge.with_notes(notes, body)` —— 统一的说明行排版

跳过某些字段时，用这个函数拼装输出。它会把 `// moonforge:` 说明行放在文件顶部、
并**与正文之间留一个空行**。

> 那个空行不是美观问题：`moon fmt` 要求独立的注释块与后面的 `///|` 之间必须有空行。
> 少了它，用户跑一次 `moon fmt` 就会让 `check` 永久报漂移，而 `gen` 又修不好。

```moonbit
let notes : Array[String] = []
notes.push("// moonforge: 跳过 " + td.name + "." + f.name + "（原因）\n")
Some(@forge.with_notes(notes, b.to_string()))
```

### `is_numeric_type(ty)` / `FieldDef::attr_args(name)` / `FieldDef::has_attr(name)`

- `td.fields` 拿到字段，`f.name` 是字段名，`f.ty` 是**源码原文**（如 `Array[Int]`、`Int?`）；
- 类型比较一律走**白名单**（`is_numeric_type` 或 `f.ty == "String"`），不要做字符串前缀猜测；
- 字段注解用 `f.attr_args("min")` 取参数、`f.has_attr("nonempty")` 查有无。

## 3. 允许生成什么：白名单纪律

这是本项目最容易踩、也最值得讲的一条。

生成物是要**提交进仓库、被 `moon check` 真实编译**的。所以"生成一段编译不过的代码"
是**最严重的 bug**——比"少生成一段代码"严重得多：后者只是功能缺失，前者会让整个项目构建失败。

因此对所有需要"类型能力"的规则（比较、转字符串、序列化），纪律是：

> **只对确定的类型生成；不确定就跳过，并在生成文件里写清原因。**

判断"确定"的依据是**类型名原文的白名单**，而不是推断：

| 需要的能力 | 白名单 | 例 |
|---|---|---|
| 可比较（`!=`） | 由 `diff` 的规则描述声明"字段类型需实现 `Eq`"，节点在 `moon check` 阶段暴露 | `diff` |
| 可 `== ""` | 仅 `String` | `validate` 的 `@nonempty` |
| 可 `<= 0` / `< n` / `> n` | `is_numeric_type` 的 8 个内建数值类型 | `validate` 的 `@positive` / `@min` / `@max` |
| 可当字符串用 | 仅 `String` | `to_pairs` |

一个反面例子（**不要这样做**）：为了让 `to_pairs` 覆盖 `Int` 字段，写成

```moonbit
// ❌ 错：字段类型未必实现 Debug，生成物编译不过
pairs.push("(\"" + f.name + "\", @debug.to_string(self." + f.name + "))")
```

正确做法是跳过 + 说明行：

```moonbit
// ✅ 对：Int 该怎么变成字符串是语义问题，工具不替用户决定
notes.push("// moonforge: 跳过 " + td.name + "." + f.name + " 的 to_pairs（类型 " + f.ty + " 不是 String；如何转成字符串由使用者决定）\n")
```

## 4. 完整样例：`to_pairs`（逐段讲解）

`rules/to_pairs.mbt` 全文约 30 行，是加规则的最小完整形态：

```moonbit
pub fn to_pairs() -> @forge.Rule {
  {
    name: "to_pairs",
    description: "为 struct 生成 T::to_pairs(self) -> Array[(String, String)]，只包含 String 字段（其余字段跳过并留说明行）",
    gen: fn(td : @forge.TypeDef) -> String? {
      if !td.has_named_fields() {          // ← 前置判断
        return None
      }
      let pairs : Array[String] = []
      let notes : Array[String] = []
      for f in td.fields {
        if f.ty == "String" {              // ← 白名单
          pairs.push("(\"" + f.name + "\", self." + f.name + ")")
        } else {
          notes.push("// moonforge: 跳过 ...（原因）\n")   // ← 说明行
        }
      }
      let b = StringBuilder()
      b.write_string("///|\n")
      b.write_string("pub fn " + td.name + "::to_pairs(self : " + td.name + ") -> Array[(String, String)] {\n")
      b.write_string("  [" + pairs.join(", ") + "]\n")
      b.write_string("}\n")
      Some(@forge.with_notes(notes, b.to_string()))        // ← 统一排版
    },
  }
}
```

生成结果的形状（`examples/models_derive_gen.mbt` 的实际片段）：

```moonbit
// moonforge: 跳过 User.age 的 to_pairs（类型 Int 不是 String；如何转成字符串由使用者决定）

///|
pub fn User::to_pairs(self : User) -> Array[(String, String)] {
  [("name", self.name), ("email", self.email)]
}
```

注意 `///|` 这一行：MoonBit 要求顶层 `pub fn` 前面有 `///|` 标记，**生成器必须自己写出来**，
否则生成物过不了 `moon check`。所有规则都遵循同样的排版骨架：

```
///|
pub fn <Type>::<方法>(...) -> ... {
  <正文>
}
```

## 5. 收尾检查清单

新规则提 PR 之前，跑一遍：

```bash
moon run cmd/main -- list-rules      # 1. 新规则出现在列表里
moon run cmd/main -- gen examples    # 2. 有输入能触发它，生成物符合预期
moon check                           # 3. 生成物真的能编译（最关键）
moon fmt && moon fmt --check         # 4. 生成物已对齐 moonfmt 的形状
moon run cmd/main -- check examples   # 5. 生成物与源文件一致（无漂移）
moon test --target js                # 6. 三类用例都过
bash scripts/e2e.sh                  # 7. 端到端 6 个阶段全过
```

第 3 步和第 4 步是**很多人会漏掉的两步**：

- 第 3 步：`gen` 成功不等于生成物正确。只有 `moon check` 编译过，才证明它是合法 MoonBit；
- 第 4 步：生成物要与 `moon fmt` 的输出字节一致。否则用户格式化一次，`check` 就永久报漂移。

把新规则的输出补进 `examples/`（输入 + 生成物一起提交），并在 `CHANGELOG.md` 的
`[未发布]` 段记一条，这样 `check` 和 CI 会持续帮你看住它。
