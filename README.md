# MoonForge

> **MoonBit 的源码到源码派生代码生成器。**
> 读取 `.mbt` 里的类型定义与 `impl @derive.DeriveXxx for T` 标记，按可插拔规则生成 MoonBit 源码，
> 并在构建前自动生成 / 校验——让"为自定义类型批量生成样板代码"变成一条命令。

[![CI](https://github.com/ZJW64/MoonForge/actions/workflows/ci.yml/badge.svg)](https://github.com/ZJW64/MoonForge/actions/workflows/ci.yml)
`Apache-2.0` · `100% MoonBit` · 公开仓库：<https://github.com/ZJW64/MoonForge>

```
$ moon run cmd/main -- list-rules

已注册的派生规则。派生入口是在类型所在文件里写一行真实 trait impl：

    pub impl @derive.DeriveXxx for <类型> with fn requested(_self) {}

  field_names
      标记 DeriveFieldNames  →  生成 impl FieldNames
      为 struct 实现 FieldNames::field_names，顺序与字段声明一致
  validate
      标记 DeriveValidate  →  生成 impl Validate
      为 struct 实现 Validate::validate，由字段注解 @nonempty/@min/@max/@positive 驱动
  diff
      标记 DeriveDiff  →  生成 impl Diff
      为 struct 实现 Diff::diff，返回发生变化的字段名（字段类型需实现 Eq）
  to_pairs
      标记 DeriveToPairs  →  生成 impl ToPairs
      为 struct 实现 ToPairs::to_pairs，只包含 String 字段（其余字段跳过并留说明行）
```

## 1. 它帮我们解决什么问题

MoonBit 的 `derive(...)` **只覆盖编译器内置的 trait 白名单**。官方文档 [E4077](https://docs.moonbitlang.com/zh-cn/latest/language/error_codes/E4077.html) 明写：

> "MoonBit 允许你为你的类型派生一些预定义特征的实现。这意味着**你无法让 MoonBit 自动派生你自定义的特征**。"
>
> 示例 `struct A(Int) derive(T)`（`T` 为用户自定义 trait）直接编译失败。

派生注册表位于编译器内部（`moonbitlang/moonbit-compiler` 的 `src/ast_derive.ml` 里是一张硬编码的 `Trait → Deriver` 哈希表），**没有对外的注册入口**；编译器也没有暴露 AST、没有 proc-macro、没有 comptime。

结果就是：一旦需要"为自定义类型批量生成**语义化**代码"——数据校验、字段名枚举、结构化 diff、Builder、访问者——开发者只有两条路：

- 逐类型手写样板代码 → **重复、易漏、随字段变更而漂移**；
- 用外部通用代码生成器 → **脱离包边界、拿不到私有字段、和 `moon build` 割裂**。

**MoonForge 在用户态补上了这个派生注册点**：不修改编译器、不依赖编译器内部 API，用"源码到源码"的方式把这类代码生成变成可测试、可持续维护的工程资产。

它是**通用 trait 派生基础设施**，不是"四条规则加一个脚本"：

- 派生目标是一个**普通的 MoonBit trait**（`FieldNames` / `Validate` / `Diff` / `ToPairs`），
  用户在自己的包里实现它、也能定义**自己的** trait 与规则；
- 规则本身是一个 trait（`DeriveRule`），规则集合是 `Array[&DeriveRule]` 的**trait 对象数组**
  —— 运行时多态，加规则不用改任何核心代码；
- 入口是**真实的 trait impl**，不是工具私有的 DSL（见第 3 节）。

## 2. 它明确不是什么

主动划清边界，避免夸大：

- ❌ **不是编译器插件**，不修改 `moonc`，不依赖任何编译器内部 API；
- ❌ **不发明语法**，不注册新的 attribute —— 入口是**本来就合法的 trait impl**，
  解析器只读它、不改它，源码在 `moon check` 下与不写标记时完全一样；
- ❌ **不做运行时反射**；
- ❌ **不声称扩展了 `derive()`** —— `derive()` 的行为完全不受影响；本项目的入口
  刻意**不用** `derive(...)`，正是因为它只认编译器内置 trait 白名单；
- ⛔ **不是编译期执行引擎**：MoonBit 目前没有 comptime，生成发生在 `moon build` **之前**的独立阶段。这一点在 [`docs/项目方案（完善版）.md`](docs/项目方案（完善版）.md) 第 5.2 与第 9 节有详细论证。

### 请求语法：一行真实的 trait impl

**两步**：引包 + 写标记。

```moonbit
// moon.pkg
import {
  "moonforge/derive" @derive,   // 别名随你起，生成的 impl 会复用它
}
```

```moonbit
/// 用户信息。
pub(all) struct User {
  /// 姓名
  /// @nonempty
  name : String

  /// 年龄
  /// @min(0) @max(150)
  age : Int

  /// 邮箱
  email : String
} derive(Eq, Debug)

/// 为 User 请求四项派生。四行 impl 的**书写顺序 = 生成物中四段 impl 的顺序**。
pub impl @derive.DeriveValidate for User with fn requested(_self) {}

///|
pub impl @derive.DeriveDiff for User with fn requested(_self) {}

///|
pub impl @derive.DeriveFieldNames for User with fn requested(_self) {}

///|
pub impl @derive.DeriveToPairs for User with fn requested(_self) {}
```

- 标记是**真实的 `impl`**：`@derive.DeriveXxx` 是 `moonforge/derive` 里的**标记 trait**（marker trait），
  方法体是空的 —— 它唯一的职责是"让编译器与 MoonForge 都能看见这次派生请求"，
  因此它**能被 `moon check` 真正编译**，而不是一段只有工具认识的注释；
- **`_self` 这个方法的唯一意义就是让标记是合法 trait impl**。MoonBit 语法不允许
  `impl T for X {}` 这种空块（`Invalid grouped impl declarations`），所以标记 trait 必须带一个方法；
- 目标 trait 路径**复用你写标记时用的包前缀**（`@derive` / `@d` / 空），
  MoonForge 不会假设你把它叫 `@derive`，生成的 impl 里原样复用；
- 书写顺序 = 输出顺序（保证生成结果字节稳定，便于人工核对）；
- `@nonempty` / `@min(n)` / `@max(n)` / `@positive` 仍写在**字段**的 doc comment 里，
  它们是**规则私有的输入**，由具体规则解释（`validate` 用得上，其余规则忽略）；
- **没有标记的类型，工具完全不碰**（零侵入）；注释必须**紧邻**声明，否则不被采纳。

> **为什么入口不用 doc comment？** 因为 `/// @derive(...)` 是一条**只有 MoonForge 认识**的私有约定：
> 它不参与类型检查，拼错了也不报错，换个工具就失效。改成真实 `impl` 之后：
> ① 入口能被 `moon check` 编译，拼错标记名会立刻报 "unknown trait"；
> ② 它是**语言级**的"这个类型请求了某个 trait"，任何工具都能读；
> ③ 第三方包可以自己定义标记 trait，MoonForge 不需要认识它。
> 老写法仍然被识别，但**不再产出代码**，而是给出可粘贴的迁移提示（见第 9 节）。

### 生成结果

`moon run cmd/main -- gen examples` 会在**源文件同目录**产出 `models_derive_gen.mbt`：

```moonbit
// ---------------------------------------------------------------------------
// Generated by MoonForge 0.3.0 -- DO NOT EDIT.
// source : models.mbt
// rules  : validate, diff, field_names, to_pairs
// entry  : impl @derive.DeriveXxx for <Type> with fn requested(_self) {}
// regen  : moon run cmd/main -- gen <dir>
// ---------------------------------------------------------------------------

///|
pub impl @derive.Validate for User with fn validate(self) {
  if self.name == "" {
    return Err("User.name must not be empty")
  }
  if self.age < 0 {
    return Err("User.age must be >= 0")
  }
  if self.age > 150 {
    return Err("User.age must be <= 150")
  }
  Ok(())
}
```

注意 impl 头**不写返回类型**：方法签名由 trait 声明唯一决定，生成的实现只提供方法体。
这不是风格偏好，而是**为了与 `moon fmt` 逐字节一致**的硬约束 —— 详见第 9 节的
"生成物的列宽预算"。

**为什么生成到同目录？** MoonBit 的包边界就是目录，私有字段只有同包可见。生成到同目录才能**直接访问字段，而不强迫你把字段改成 `pub`**。代价是会往你的源码目录里写文件——用文件头的 `DO NOT EDIT` 声明把它和手写代码区分开。

> **生成文件是应该提交进仓库的，不要写进 `.gitignore`。**
> 提交之后 `moon check` 就会真实地编译它，生成代码的正确性由编译器裁决，
> 而不是由工具的自我声明裁决；同时 `moon run cmd/main -- check` 才能拿磁盘上的
> 生成物和源文件对比，检出"改了源码却忘记重新生成"的漂移。
> 把生成物藏进 `.gitignore` 会同时失去这两道防线 —— 这正是 `go generate` 一类
> 工具踩过的坑，本项目的取舍是明确站"提交"这一边。
> 仓库里的 `examples/models_derive_gen.mbt` 就是按这个约定提交的样板。

## 4. 内置规则

| 规则 | 标记 trait | 生成物 | 前置条件 |
|---|---|---|---|
| `field_names` | `DeriveFieldNames` | `impl FieldNames`：按声明顺序返回字段名 | 无 |
| `validate` | `DeriveValidate` | `impl Validate`：按字段注解逐项校验 | 注解只在 `String` 与内建数值类型白名单上生效 |
| `diff` | `DeriveDiff` | `impl Diff`：返回发生变化的字段名 | 字段类型需实现 `Eq` |
| `to_pairs` | `DeriveToPairs` | `impl ToPairs`：键值对，只含 `String` 字段 | 非 `String` 字段跳过并留 `// moonforge:` 说明行 |

四条规则**都要求类型有具名字段**。给 enum 加上标记不会报错，而是得到一条"不适用"诊断；给位置参数结构体（`struct Point(Int, Int)`）加上标记同理 —— 它确实是 struct，但"按字段名展开"对它没有意义，工具**拒绝生成并说清原因**，而不是生成一个语法说得通、语义完全错误的 `field_names() { [] }`。

`validate` 的注解语义：

| 注解 | 生效类型 | 生成 |
|---|---|---|
| `@nonempty` | `String` | `if self.f == "" { return Err(...) }` |
| `@positive` | `Int` / `Int16` / `Int64` / `UInt` / `UInt16` / `UInt64` / `Double` / `Float` | `if self.f <= 0 { ... }` |
| `@min(n)` | 同上 | `if self.f < n { ... }` |
| `@max(n)` | 同上 | `if self.f > n { ... }` |

注解落在白名单之外的类型上时，规则**跳过**它并在生成文件里留下说明行：

```moonbit
// moonforge: 跳过 Order.quantity 的校验注解（类型 Int 不在 String / 内建数值类型白名单内）
```

宁可少生成，也不生成编译不过或语义可疑的代码；而"**为什么不生成**"同样是要被解释的信息。

## 5. 命令参考

| 命令 | 作用 |
|---|---|
| `moonforge list-rules` | 列出已注册规则（含各自的标记 trait） |
| `moonforge explain <file.mbt>` | 打印解析结果（类型 / 字段 / 注解 / 命中的 impl 标记），用于调试与可解释性 |
| `moonforge gen <path...>` | 生成 `*_derive_gen.mbt`（path 可为文件或目录，目录只扫描一层） |
| `moonforge check <path...>` | 校验生成物是否漂移；**有漂移则以非零码退出**（CI 用） |

退出码约定：`0` 成功 · `1` 检出漂移 · `2` 参数或路径有误。

任何错误都归一成**一行** `moonforge: ...` 提示，不会把运行期堆栈喷进 CI 日志：

```
$ moon run cmd/main -- explain validate
moonforge: 找不到路径：validate
    用法：moonforge explain <file.mbt>，例如 moonforge explain examples/models.mbt
```

`explain` 的实际输出（节选）：

## 6. 接进构建流程

生成器是 `moon build` **之前**的独立阶段（MoonBit 没有编译期钩子）。两种接法：

```bash
# 日常开发：改完源码跑一次
moon run cmd/main -- gen src

# CI：校验生成物没有漂移（改了源码却忘记重新生成 → 非零退出）
moon run cmd/main -- check src
```

`.github/workflows/ci.yml` 已经接好了这条链路。

## 7. 架构

```
 .mbt 源码
    │ (1) 词法分析        lexer.mbt        —— 只切 token，字符串/注释整体跳过
    ▼
 Token 流
    │ (2) 子集语法分析    parser.mbt       —— 花括号深度 0 认 struct / enum，
    ▼                                        并识别 `impl <前缀>.<标记> for <类型>`
 类型模型 IR           type_model.mbt   —— TypeDef / FieldDef / Attr / BodyKind
    │ (3) 规则分派        rule.mbt         —— 标记 trait → &DeriveRule（trait 对象）
    ▼
 代码片段              rules/*.mbt      —— field_names / validate / diff / to_pairs
    │ (4) 组装 + 文件头   codegen.mbt      —— 幂等、字节稳定、列宽受预算约束
    ▼
 <同目录>/<主干名>_derive_gen.mbt
    │ (5) 和手写代码一起编译
    ▼
 moon check / moon test / CI
```

### 可扩展性：规则是一个 trait，注册表是一个 trait 对象数组

派生目标 trait 与标记 trait 都定义在 `moonforge/derive`：

```moonbit
// 派生目标：用户在自己的包里实现它，生成物提供实现
pub trait FieldNames {
  fn field_names(Self) -> Array[String]
}

// 标记：用户写一行 impl 就等于提交一次派生请求
pub trait DeriveFieldNames {
  fn requested(Self) -> Unit
}
```

规则本身是一个 SPI trait，规则集合是**异构的 trait 对象数组**：

```moonbit
pub(open) trait DeriveRule {
  fn head(Self) -> RuleHead                    // 规则键 / 标记名 / 目标 trait 名 / 描述
  fn generate(Self, TypeDef) -> Fragment?      // None = 该规则不适用于这个类型
}

pub fn all() -> Array[&@forge.DeriveRule] {
  [
    FieldNamesRule::{ } as &@forge.DeriveRule,
    ValidateRule::{ } as &@forge.DeriveRule,
    DiffRule::{ } as &@forge.DeriveRule,
    ToPairsRule::{ } as &@forge.DeriveRule,
  ]
}
```

**新增一条规则 = 新增一个文件 + 在 `rules/registry.mbt` 的数组里加一项 + 补一组测试。**
不需要修改词法、语法、代码生成等任何核心代码。

`examples/extension/` 是一个**可运行的第三方扩展样例**：它自带一个 `ToCsv` trait 与
`DeriveToCsv` 标记、一个 `ToCsvRule`，把内置规则和自己的规则合成一个新集合后直接生成 ——
全程**没有修改 moonforge 的任何源码**，并有独立测试证明它生效（`examples/extension/tocsv_wbtest.mbt`）。
规则指南见 [`docs/扩展规则指南.md`](docs/扩展规则指南.md)。

## 8. 测试策略

| 层 | 覆盖对象 | 文件 |
|---|---|---|
| L1 | 词法：行首判定、注释剥离、字符串里的花括号不泄漏、非 ASCII 标识符、越界哨兵 | `lexer_wbtest.mbt` |
| L2 | 语法：类型原文精确切片（泛型 / 可选 / 包名 / 元组 / 函数类型 / 尾随逗号）、注释紧邻性、深度守卫、enum 变体、**位置参数结构体不吞并后续声明**、**impl 标记的识别**（包前缀 / 泛型目标 / 固有 impl 不算标记 / impl 体内的花括号不污染扫描）、不完整输入不崩溃 | `parser_wbtest.mbt` |

| L7 | 端到端 CLI：`gen` 后 `check` 返回 0；改动源文件后 `check` 返回非零 | `scripts/e2e.sh` + CI |
| L8 | CLI 地基：argv 前缀归一化、`is_command` 白名单、路径拆分与拼接（正 / 反斜杠） | `cmd/main/main_wbtest.mbt` |
| L9 | 格式与换行：仓库自身通过 `moon fmt --check`；生成物与 `moon fmt` 的字节一致（否则格式化一次就永久报漂移）；生成物被换成 CRLF 后 `check` 仍须通过；**列宽预算用真实 `moonfmt` 现场实测** | `scripts/e2e.sh` 第 4 / 5 阶段 + `scripts/fmt_budget_probe.sh` + CI |
| L10 | 契约与闭环：漂移 → 退出码 1，`gen` 后回到 0；路径不存在 / 非 `.mbt` / 传目录 → 退出码 2；源码去掉派生标记后 `gen` 清理残留生成物 | `scripts/e2e.sh` 第 6 阶段 + CI |
| L11 | 扩展性证据：第三方规则不改内核即可注册生效、前缀复用、只用自定义规则时内置规则完全不出场、未注册标记被明确报出 | `examples/extension/tocsv_wbtest.mbt` |

`examples/models_wbtest.mbt` 里的测试**直接调用自动生成的方法**：

```moonbit
@debug.debug_inspect(@derive.Validate::validate(u), content="Err(\"User.name must not be empty\")")
@debug.debug_inspect(@derive.Diff::diff(a, b), content="[\"age\"]")
@debug.debug_inspect(@derive.ToPairs::to_pairs(u), content="[(\"name\", \"Ada\"), (\"email\", \"ada@example.com\")]")
```

这些方法在本仓库里没有任何手写实现——这就是"生成代码真的能用"的最直接证据。

```bash
$ moon test --target js
Total tests: 119, passed: 119, failed: 0.

$ moon test --target wasm-gc
Total tests: 119, passed: 119, failed: 0.
```

> 换一个后端再跑一遍是有意义的：js 与 wasm-gc 的整数语义、字符串表示都不同，
> 生成代码不能只在其中一个后端成立。CI 里两个后端都会跑。

> **L6 是这套设计最关键的一条**：它把"工具输出的代码是正确的"从"我说它对"变成"编译器说它对"。

## 9. 已知限制（诚实清单）

| 限制 | 说明 | 影响 |
|---|---|---|
| 只解析**顶层类型定义** | 函数体 / 表达式 / 宏只做括号计数并整体跳过 | 类型定义写在函数体内部（MoonBit 里不常见）不会被识别 |
| 字段类型**不做语义分析** | 取源码原文，由规则按字符串判断 | 别名类型（`type Age = Int`）不在数值白名单里，`@min` 会被跳过并留说明行 |
| 注解只写在一行 | `@min(0)` 的参数不支持换行书写 | 多行注解需写在同一行 |
| 字段注解的 doc comment 必须**紧邻**字段 | 中间有空行则不被采纳 | 靠 `explain` 一眼可查 |
| **生成物的列宽预算 82 列** | 生成的 impl 头超过 82 列时，`moon fmt` 会把它折开，导致生成物与格式化结果不一致、`check` 报漂移（而 `gen` 也治不好）。所以生成的 impl 头**不写返回类型**（返回类型由 trait 声明决定），为类型名与方法名留出约 20 列余量；真的超了会在生成阶段给出可操作的诊断 | 类型名极长（≳ 21 列）时需缩短、或给包起更短的别名。预算值由 `scripts/fmt_budget_probe.sh` 用真实 `moonfmt` 实测钉住 |
| `diff` 依赖字段类型的 `Eq` | 生成 `!=` | 前置条件已写进规则描述；节点在 `moon check` 阶段暴露 |
| 目录只扫描一层 | 避免误扫 `_build/` | 深层目录请显式传多个路径 |
| 生成文件头只写**文件名** | 不写绝对路径 | 保证跨机器字节稳定；同名文件在不同目录下的头部相同（不影响内容） |
| 只处理**有具名字段的 struct** | enum、位置参数结构体（`struct Point(Int, Int)`）、无字段体声明都不产出代码 | 给它们加标记是**安全**的：得到"不适用"诊断而不是报错，`explain` 会显示 `struct(位置参数)` |
| 标记 impl **跨文件不生效** | 只在同一文件内建立"标记 → 类型"的对应关系 | 标记要写在类型所在文件；写错位置会得到"本文件里没有定义"的诊断 |
| 老写法 `/// @derive(...)` 已废弃 | 仍被识别，但**不再产出代码**，给出一条**可粘贴的**迁移提示 | 升级时不会"生成物莫名消失" |
| Windows 上的 CRLF | 读取生成物时先把 CRLF / 单独 CR 折叠成 LF 再比较、再解析 | `core.autocrlf=true` 的检出不会造成误报漂移（`.gitattributes` 也把 `*.mbt` 钉成 LF） |
| 残留生成物由 `gen` 清理 | 源文件里已经没有派生标记时，`gen` 会删除同名 `*_derive_gen.mbt` | 避免 `check` 一直报"多余的生成文件"，而照提示跑 `gen` 又修不好的死循环 |
